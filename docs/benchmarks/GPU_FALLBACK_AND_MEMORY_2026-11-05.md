# 전체 CPU 전환과 메모리 예산 점검 — 2026-11-05

미배포 1.38.0에서 GPU 지원 범위 확장 후 추가 점검한 기록이다.
일반적인 PDF 기능의 미지원과 복잡도·용량·장치 한도 초과를 구분했다.

## 실제로 고친 전체 CPU 전환

- 시작점과 끝점이 같은 축 그라데이션: MuPDF CPU 기준에서 잉크가 없는 무효 그리기다.
  전체 페이지를 거부하던 오류를 없애고 해당 그라데이션만 생략한다.
- Type3 한 글자의 프로그램이 캡처 한도를 넘는 경우: 해당 글자를 제한된 CPU 이미지로
  보정하고 나머지 페이지는 GPU로 유지한다. 한도는 없애지 않았다.
- GPU 최대 크기를 넘는 긴 이미지: 표시용 비트맵을 8192픽셀 이내로 준비한다.
  고배율에서 요청한 작은 영역은 원본 이미지 전체의 폭에 맞춰 축소하지 않는다.

깊게 중첩된 패턴도 벡터 확장 깊이 8에 도달하면 원래 타일 프로그램을 영역 보정에 넘긴다.
빈 이미지·채움은 생략하고, 빈 채움 클립은 내용 스코프까지 생략한다.
굵기 0인 선과 stroke clip은 보이는 hairline일 수 있으므로 이 생략 조건에 넣지 않는다.

## 메모리 변경

| 대상 | 이전 | 이후 |
| --- | ---: | ---: |
| 페이지 이미지 자원 합계 | 64 MiB | 128 MiB |
| 페이지 전체 자원 | 128 MiB | 256 MiB |
| 작업 프로세스·저장 패킷 | 256 MiB | 512 MiB |
| 개별 보정/샘플링 표면 | 약 16 MiB | 약 32 MiB |

필요한 만큼만 할당한다. CPU 타일 캐시와 RAM·VRAM 상황에 맞춰 회수하는 기존 캐시 정책은
유지한다. 위 값은 데이터 종류별 한도이며 프로세스 전체 사용량이나 VRAM 총량 한도가 아니다.

72 MiB 이미지 시험 PDF의 실제 결과:

| 항목 | 이전 | 이후 |
| --- | ---: | ---: |
| 준비된 GPU 패킷 | 46.09 MiB | 72.00 MiB |
| 준비 작업 프로세스 peak working set | 170.5 MiB | 231.1 MiB |
| GPU 표시 | 성공 | 성공 |

이미지를 더 많이 축소하던 이전 경로보다 원본 샘플을 더 유지하며, 그만큼 RAM도 더 사용한다.
20000픽셀 폭의 별도 시험 이미지에서는 이전 GPU 업로드가 `0x80070057`로 실패했고,
수정 후 GPU 프레임을 생성했다. 고배율 영역 요청이 원본 픽셀을 유지하는지도 회귀 검사한다.

## 검증과 남는 조건

- 보유 PDF 36쪽과 재현 PDF 9쪽, 총 45쪽을 새 작업 프로세스로 준비하고 GPU 프레임까지 생성했다.
  이 범위에서는 전체 CPU 전환이 없었다.
- 72 MiB 장면의 Python 저장 왕복, 네이티브 작업 프로세스, 실행 파일 호환 작업 경로를 검증했다.
- 128 MiB를 넘는 선언된 이미지 데이터는 픽셀 복사 전에 거부되는지 확인한다.
- 자동 테스트 860개와 변경된 GPU·전송·캐시 경로의 후속 회귀 검사를 통과했다.
- 렌더러 ABI 26, 입력 ABI 3, 장면 저장 의미 버전 21을 함께 사용한다.

모든 PDF가 GPU로 표시된다는 보장은 아니다. 페이지 전체의 명령·경로·확장 수와 스코프
깊이 한도, 이미지 128 MiB·전체 자원 256 MiB·패킷 512 MiB 한도,
시간 초과, 손상된 데이터, 장치·라이브러리 오류가 남는다. 보정 영역까지 계산할 수 없는
이 조건에서는 페이지 전체의 CPU 타일 표시 경로를 유지한다.

CMYK, 일반 투명도·패턴·메시라는 기능 이름만으로 페이지를 CPU로 바꾸지는 않는다.
CMYK와 일부 합성의 GPU 표현은 근사이며, 정확한 색상 확인에는 CPU 모드를 사용한다.
