# JPEG 원본 전달과 GPU 색 변환 비교

처음 측정은 작은 BGRA 미리보기가 더 작으면 기존 경로를 선택하던 시점의 결과다. 현재는 사용자의 확대·축소 우선 요청에 따라 그 용량 기준을 제거했다. 최신 동작과 별도 비교는 마지막의 **작은 미리보기 후속 변경**에 기록한다.

## 범위

- 기준: `e2d20e49`의 MuPDF 어댑터, Rust 컴파일러, D2D DLL을 별도로 보관해 비교.
- 장비: Intel Iris Xe Graphics, Windows, 같은 Python/PyMuPDF 환경.
- 입력: 결정적인 색상·도형을 담은 1600×1200 JPEG를 DeviceRGB 이미지로 삽입한 256×256 PDF.
- 각 모드·준비 배율에서 예열 1회 후 5회 측정. 이를 3쌍 반복하고 두 번째 쌍은 새 경로부터 실행. 아래 값은 각 쌍 중앙값의 중앙값.
- PDF를 새로 열고 네이티브 장면도 새로 생성. 측정은 컴파일·패킷 생성부터 GPU 업로드·첫 프레임 픽셀 읽기까지. 앱 시작, 프로세스 시작, 디스크 I/O와 실제 스크롤 시간은 포함하지 않는다.
- 준비 배율은 1배와 4배이며, 표시 영역은 1200×900에 고정해 페이지를 맞췄다. 따라서 4배는 400% 표시를 위한 이미지 자원 준비 비용을 비교한 것이며, 실제 UI의 400% 스크롤 벤치마크가 아니다.
- 원시 자료와 재실행 스크립트는 로컬 `.test-runtime/jpeg-gpu/`에 보관. `old-photo-pair{1,2,3}.json`, `new-photo-pair{1,2,3}.json`, `bench.py`, 원본 PDF 및 출력 PNG 포함.

## 결과

| 준비 배율·항목 | 기존 | JPEG 경로 |
|---|---:|---:|
| 1배 컴파일·업로드·첫 표시 합계 | 16.03ms | 16.46ms |
| 4배 컴파일·패킷 생성 | 36.86ms | 1.22ms |
| 4배 네이티브 GPU 자원 업로드 | 5.19ms | 12.51ms |
| 4배 첫 프레임 표시·읽기 | 7.54ms | 7.84ms |
| 4배 컴파일·업로드·첫 표시 합계 | 49.79ms | 22.42ms |
| 4배 RAM 장면 패킷 | 2,242,221B | 267,328B |
| 4배 LZ4 저장 봉투 | 1,497,009B | 146,616B |

각 구간 중앙값의 합은 합계 중앙값과 일치하지 않을 수 있다.

4배 준비·첫 표시 합계는 약 55.0% 줄었고, RAM 패킷은 88.1%, 압축 저장 크기는 90.2% 줄었다. 이 초기 비교의 1배에서는 JPEG 원본이 작은 BGRA 미리보기보다 커서 기존 경로를 선택했고, 두 출력 픽셀은 완전히 같았다. 1배의 0.43ms 차이를 성능 개선으로 해석하지 않는다.

4배 출력의 RGB 채널 평균 절대 차이는 255단계 중 약 0.282(전체 표시 영역 기준 약 0.11%)이고, 최대 채널 차이는 25다. 색 경계에서 보간 결과가 달라질 수 있으며, 원본 JPEG를 재압축하거나 색차 정보를 추가로 줄이지 않는다.

`jabc-68-22.pdf` 첫 페이지도 함께 확인했다. 작은 JPEG 로고는 기존 경로를 선택했고 장면 패킷은 버전 표식을 제외하면 동일했다. 전체 시간은 1배 192.4→174.0ms, 4배 178.7→184.0ms로 변동했으나, 새 JPEG 경로가 선택되지 않았으므로 개선 효과로 주장하지 않는다. 텍스트·벡터 중심 문서 전체가 55% 빨라진다는 의미가 아니다.

## 처리 경로와 제한

1. MuPDF 어댑터가 변형 없는 불투명 RGB JPEG의 원본 DCT 스트림을 전달한다. DeviceRGB 및 엔진 기본 sRGB와 ICC 프로필 해시가 정확히 일치하는 경우만 허용한다.
2. Rust는 JPEG를 해독하거나 픽셀별 Python 객체를 만들지 않고 LFSC v3 자원에 보관한다. RAM/LZ4/SQLite 왕복과 독립 네이티브 작업자도 이 바이트를 유지한다.
3. D2D 업로드 시 WIC의 평면 처리를 지원하는 스케일러로 필요한 크기만 준비하고 `ID2D1ImageSourceFromWic`에 넘긴다. 지원되는 GPU에서는 YCbCr 확대와 RGB 변환을 처리하며, 지원되지 않으면 WIC BGRA 업로드로 대체한다.
4. 완성된 화면 자원은 WIC 원본 참조·CPU 임시 버퍼를 해제하고 같은 장치의 보존 장면/작업자 사이에서 공유한다.

JPEG 엔트로피 해독과 IDCT는 CPU에 남는다. 현재는 이 작업이 네이티브 GPU 자원 업로드에 포함되어 그 구간은 약 5.2→12.5ms로 늘었다. 전체 준비 시간과 패킷 전달 비용은 줄었지만, GPU 업로드가 완전히 비동기로 바뀐 것은 아니다. 이미 준비한 장면의 프레임 표시 시간 개선도 주장하지 않는다.

CMYK·회색조·다른 ICC 프로필, PDF Decode/색상 키/알파 마스크·개별 불투명도, 잘라낸 부분 영역은 기존 MuPDF 경로를 유지한다. 원본이 16Mi픽셀 또는 한 축 8192픽셀을 초과해도 기존 제한된 디코더를 선택한다. 이 조건 때문에 페이지 전체 GPU 처리가 실패하지 않도록 별도 회귀 검사를 둔다. 초기의 BGRA 미리보기 용량 비교 조건은 후속 변경에서 제거했다.

GPU 보존 예산은 작은 JPEG 파일 크기뿐 아니라 풀린 BGRA 크기도 보수적으로 반영한다. 실제 DXGI 사용량은 전체 장치 자원·할당 단위·드라이버 상태의 영향을 받아 이번 소형 샘플로 일정한 VRAM 절감 수치를 주장하지 않는다. RAM 패킷과 LZ4 크기는 실제 측정값이다.

첫 구현에서 렌더러 ABI 27, 네이티브 입력 ABI 4, 장면 LFSC v3, 디스크 캐시 형식 24로 맞췄다. 후속 변경의 캐시 형식은 25다. 이전 장면 캐시는 새 형식으로 다시 준비한다. 앱 버전은 미배포 1.39.2를 유지한다.

## 검증

- JPEG 4:4:4/4:2:2/4:2:0, 프로그레시브, 90/180/270도 회전을 실제 D2D 직접 표시와 보존 작업자에서 비교.
- 원본 바이트 유지, RAM/LZ4·네이티브 프로세스·SQLite 왕복, ICC/Decode/CMYK/회색조/알파 마스크, 작은 미리보기, 고배율 영역·페이지 자르기·대형 JPEG의 대체 경로 확인.
- 손상된 JPEG, 이전 장면 버전, 잘못된 이미지 합계를 거절한 뒤 GPU 표면이 계속 사용 가능한지 확인.
- 네이티브 빌드는 MSVC `/W4 /WX`, Rust 확장·독립 작업자 빌드 완료.
- 관련 컴파일러·작업자·D2D·리더·이미지·캐시·메모리 검사 288개 통과. Python 구문, 앱/설치 버전 일치, `git diff --check` 확인.

구현 근거: [Microsoft JPEG YCbCr 설명](https://learn.microsoft.com/en-us/windows/win32/wic/jpeg-ycbcr-support), [Direct2D 원본 해제 옵션](https://learn.microsoft.com/en-us/windows/win32/api/d2d1_3/ne-d2d1_3-d2d1_image_source_loading_options).

## 작은 미리보기 후속 변경

- JPEG 원본이 작은 BGRA 미리보기보다 커도 지원되는 RGB JPEG는 네이티브 GPU 경로로 전달한다. 압축된 원본은 RAM 장면에 남고, GPU의 실제 이미지 크기와 기존 메모리 예산은 유지한다. 작은 화면 크기에서는 RAM 패킷이나 최초 업로드 비용이 이전 정책보다 늘 수 있다.
- 모든 이미지 자원이 원본 해상도까지 준비된 JPEG인 장면은 `image-downsample`을 붙이지 않는다. 같은 벡터·JPEG 장면을 확대 시 다시 컴파일하거나 GPU에 다시 올리지 않는다.
- 축소된 JPEG가 하나라도 남거나, 원본 해상도가 보장되지 않는 일반 래스터 자원이 섞이면 확대 시 보완 작업을 유지한다. 무조건 저해상도 이미지를 고정하지 않는다.
- 이 준비 정책과 배율 재사용 판단이 바뀌므로 캐시 키 형식을 25로 올려 기존 판단 결과를 다시 만들도록 했다.

### 실제 GPU 확대 반복 비교

직전 개발본의 MuPDF DLL·Rust 확장을 별도로 보관해 비교했다. 192×160 JPEG가 포함된 같은 PDF를 열고 표시 배율을 `1→2→4→8→4→2→1→16→32` 순서로 바꿨다. 첫 준비 후에는 현재 장면에 확대 보완이 필요할 때만 `Document.gpu_vector_page`를 요청하고, 장면이 바뀔 때만 GPU에 업로드했다. 실제 D2D 보존 작업자 표시와 화면 읽기를 함께 실행했다. 프로세스를 분리해 각각 3회 반복했다.

| 항목 | 직전 정책 | 후속 변경 |
|---|---:|---:|
| 전체 컴파일 횟수 | 6회 | 1회 |
| 전체 GPU 업로드 횟수 | 6회 | 1회 |
| 첫 준비를 제외한 확대 반복의 준비·업로드 합계 중앙값 | 10.29ms | 0.014ms |
| 첫 준비 포함 준비·업로드 합계 중앙값 | 23.47ms | 17.64ms |

표시·화면 읽기 자체의 중앙값은 251.5→253.3ms로 변동했고 개선을 주장하지 않는다. 이 값에는 보존 작업자의 완료 대기와 화면 읽기가 포함되어 실제 UI 애니메이션 FPS 측정이 아니다. 이번 검증은 **원본 픽셀이 이미 준비된 JPEG의 불필요한 재컴파일·재업로드 제거**를 확인한다.

원시 자료는 `.test-runtime/jpeg-preview-gpu/zoom-{before,after}-{1,2,3}.json`과 `bench-zoom.py`에 보관한다. 작은 JPEG의 경로 선택, 3200% RAM 장면 재사용, 실제 GPU 장면을 유지한 확대·이동, 혼합 래스터 장면의 보완 유지, 작업자·디스크·RAM 캐시 등 관련 검사 176개를 통과했다.
