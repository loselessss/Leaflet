# 작은 복합 삽화의 영역 단순화 조사

조사일: 2026-10-23 · Leaflet 1.37.1 개발 중 · Intel Iris Xe · ABI 24

## 판단

**ACB 2015를 성능 기준에서 제외하기 전에 시도할 만한 큰 후보를 찾았다.** 결과 도식의 작은 단백질·효소 삽화에 장면 명령 대부분이 몰려 있다. 이 삽화의 복잡한 벡터·클립·투명도 그룹을 작은 영역 이미지로 대체하면 제출하는 명령 수를 크게 줄일 수 있다.

단순히 Normal 그룹을 제거하거나 knockout을 끄는 후보는 유의미한 속도 개선이 없었다. 반면 작은 복합 삽화를 CPU로 영역 렌더링하고 나머지를 기존 GPU로 그리는 실험에서는, **각 작업마다 영역 이미지를 새로 만드는 비용까지 포함한 중앙값**이 두 번의 비교에서 모두 개선됐다. 결과 이미지 캐시를 재사용한 비교가 아니다.

이 작업은 후보 탐색과 개인 실험까지다. **기본 앱 동작·native DLL은 변경하지 않았다.** 공개 분석 도구만 추가했다. 영역의 색과 경계에는 눈에 보이는 차이가 있고 최초 문서 준비 비용도 남아 있어 제품 적용 완료로 판단하지 않는다.

## 어디에 복잡도가 몰려 있는가

Python 장면 추출 결과를 그룹·클립·마스크 트리로 분석했다. 아래 수는 PDF 원본 객체 수나 native 최종 명령 수가 아니다. native의 빈 레이어 제거 이전 장면 항목 수다.

| 항목 | ACB 2015 | ACB 2019 |
|---|---:|---:|
| 장면 항목 | 33,260 | 323 |
| GroupPush | 3,211 | 1 |
| ClipPush | 8,445 | 53 |
| MaskBegin | 193 | 23 |
| 최대 scope 깊이(루트 포함) | 16 | 4 |
| 선택된 작은 복합 그룹 | 25 | 0 |

선택 조건은 격리된 Normal·opacity 1 knockout 그룹, subtree 128항목 이상, bbox 면적이 페이지의 0.5% 이하, mask 생성 중이 아닌 것이다. 바깥 그룹을 선택하면 그 안의 그룹을 다시 세지 않는다. 이것은 탐색 기준이며 자동 대체의 안전성 증명이 아니다. bbox는 기존 장면 분석 함수의 도형 경계 추정이고, 실제 칠한 픽셀 면적이나 clip 교집합 면적이 아니다.

- 25개 그룹이 **28,615항목, 전체의 86.03%**를 차지한다.
- 25개 bbox의 면적 합은 페이지의 **약 0.265%**다. bbox끼리 중첩할 수 있으므로 정확한 union 면적은 아니다.
- 가장 복잡한 작은 그룹은 1,699항목이다. bbox는 약 61.2×25.6 PDF point다.
- 각 그룹을 이미지 하나로 대체하면 4,670항목이다. 가까운 그룹을 묶어 7개 영역으로 만들면 **4,652항목, 약 86.0% 감소**다.
- 이 사례의 병목은 포스터 전체 배경 그래디언트만이 아니라, 화면에서 작게 보이는 삽화의 내부 표현에 특히 집중돼 있다.

원본 메타데이터도 비교했다. 2015는 Adobe Illustrator CC 2015 / Adobe PDF library 10.01, 2019는 PowerPoint / macOS Quartz PDFContext이며 둘 다 PDF 1.4다. 서로 다른 프로그램·디자인의 문서이므로 **2019년에 같은 exporter의 구조 최적화가 개선됐다는 결론은 내릴 수 없다.**

## 비교한 후보

### 그룹 경계만 제거

1. knockout 조상 아래를 보호하면서 opaque Normal 그룹을 제거: 33,260 → 32,932항목.
2. knockout을 끄고 opaque Normal 그룹을 더 넓게 제거: 33,260 → 27,258항목.

비Normal blend를 포함한 subtree는 유지했다. 7회 비교의 요청→sharp 완료 중앙값은 2015 맞춤 330.78→331.50/327.84ms, 100% 407.05→437.24/418.76ms, 200% 185.02→190.83/209.90ms였다. 마스크·클립·개별 도형이 여전히 많아 이 후보를 채택할 근거가 없었다. 2019는 변환 전후 명령·저장 화면이 같았다. 이는 기존 실험과 같은 sharp 완료 지표이며 아래 영역 후보의 전체 작업 지표와 직접 비교하지 않는다.

### 영역 전체를 새 이미지로 만들기

- 원본을 수정하지 않고, 입력 MuPDF display list에서 선택한 작은 영역만 CPU로 렌더링한다.
- **매 표본마다 현재 배율과 viewport에 맞는 새 픽셀과 GPU bitmap을 만든다.** 이전 이미지나 이전 확대 배율의 결과를 재사용하지 않는다. 입력 display list와 불변 GPU geometry는 준비된 상태다.
- 첫 후보는 25개의 개별 영역이었다. 다음 후보는 가까운 영역을 7개로 묶었다. 묶음 조건은 bbox 간 거리 12point 이하, 합친 bbox 면적이 기존 bbox 면적 합의 4배 이하, 가장 긴 변 128point 이하다.
- 원래 25개 subtree를 제거하고, 7개 영역 이미지를 남은 장면의 마지막에 덮어 그린다. 영역은 흰 배경을 포함한 원본 전체 페이지의 해당 crop이다. 따라서 원래 subtree만 투명 배경으로 렌더링한 독립 group texture와는 다르다.
- 나중에 그린 객체를 crop에 포함한 뒤 다시 합성하는 것을 피하려고 최종 덮어쓰기를 사용한다. 영역 안에 있는 주변 글자·선도 이 crop으로 덮인다. 일반 문서에서의 적용에는 배경·z 순서·페이지 밖 clip·색 관리와 경계 검증이 더 필요하다.
- CPU 픽셀 격자를 GPU 화면의 확대·이동 원점에 맞추고, crop에 최소 1화면 픽셀의 여유를 둔다. 화면 밖 영역은 만들지 않는다. 이 실험은 CPU/GPU 혼합 렌더링이며, 복잡한 투명도 계산을 모두 GPU에서 근사한 구현은 아니다.

## 영역 후보 측정

기준 DLL은 256슬롯 수명 계획을 포함한 현재 개발 빌드다. SHA256:

`8edb5e56aeab510c4c8df410de8f09f09598b367b430d56683920bb6ecdbc336`

1200×900 viewport, 96 DPI, 장면 raster scale 1, 맞춤·100%·200%를 비교했다. 조건마다 3회 예열 후 15회 측정하고 baseline/candidate 순서를 번갈아 실행했다. 다른 GPU 테스트·빌드는 동시에 실행하지 않았다.

**타이머 안:** 후보의 CPU crop 생성·BGRA 변환·새 bitmap upload, 양쪽의 새 retained scene 생성, worker sharp 완료, 진단 readback·프레임 종료. **타이머 밖:** 초기 PDF 해석·Python 장면 추출, 불변 geometry 준비, 입력 display list 생성. 따라서 앞선 GPU 보고서의 sharp 완료 시간과 절대값을 직접 비교하지 않는다. 매 표본 새 scene identity를 사용했고, 새 후보 bitmap은 표본 종료 후 해제했다. 단위 ms.

| 배율 | 1차 기준 | 1차 영역 후보 | 단축 | 재측정 기준 | 재측정 영역 후보 | 단축 |
|---|---:|---:|---:|---:|---:|---:|
| 맞춤 | 414.46 | 169.76 | 59.0% | 424.17 | 110.19 | 74.0% |
| 100% | 383.89 | 118.04 | 69.3% | 396.82 | 100.54 | 74.7% |
| 200% | 251.85 | 84.75 | 66.4% | 295.66 | 101.47 | 65.7% |

재측정의 CPU crop·업로드 등 준비 중앙값은 맞춤 53.91ms, 100% 47.55ms, 200% 43.09ms다. 생성한 영역은 각각 7/4/2개이고, 이미지 픽셀 합은 2,693/5,440/12,504픽셀이다. 논리 BGRA 데이터는 약 10.5/21.3/48.8KiB지만 입력 display list·드라이버·GPU allocation까지 포함한 메모리 절감 실측은 아니다.

P95는 여전히 불안정하다. 15회 nearest-rank P95는 최댓값이며, 1차 기준/후보는 맞춤 1430.10/1187.31ms, 100% 1406.57/1125.18ms, 200% 1411.18/1126.77ms였다. 재측정은 1452.42/621.65ms, 1491.18/1170.93ms, 1412.77/1133.84ms였다. 중앙값의 큰 개선과 별개로 긴 지연이 해결됐다고 주장하지 않는다. 이 지표는 CPU 준비와 driver/readback 경과를 포함하며 GPU 활성 시간만의 측정도 아니다.

추가 입력 display list 생성에는 두 실행에서 약 187/188ms가 들었다. 최초 전체 페이지 표시 시간은 측정하지 않았다. 현재는 기존 장면 추출도 그대로 하므로 초기 해석 시간을 줄였다는 뜻이 아니다. 제품 단계에서는 작은 복합 그룹을 수만 개 Python 항목으로 확장하기 전에 식별하는 방향을 검토해야 한다.

## 화면 차이와 적용 한계

Poppler로 원본 전체 페이지를 확인하고, 기본 GPU 화면·후보 전체 화면·7개 확대 crop을 확인했다. 두 15회 실행에서 저장한 후보의 맞춤·100%·200% 화면은 서로 byte 단위로 같았다.

| 배율 | 기준과 다른 픽셀 | 전체 화면 비율 | 최대 채널 차이(0~255) | 전체 BGRA 평균 절대 차이 |
|---|---:|---:|---:|---:|
| 맞춤 | 2,727 | 0.253% | 205 | 0.036 |
| 100% | 5,454 | 0.505% | 189 | 0.052 |
| 200% | 12,566 | 1.164% | 190 | 0.077 |

**작은 픽셀 차이만 있는 결과는 아니다.** 작은 삽화의 색이 밝아지고 가장자리·주변 작은 글자의 AA가 달라진다. 변경 영역은 작지만 그 안의 최대 차이는 크다. 패딩한 영역에서 2픽셀 더 확장한 사각형 밖에도 20/25/65픽셀이 달랐고 최대 채널 차이는 2였다. 차이가 완전히 영역 안에만 있다고 주장하지 않는다.

이 문서는 후보 탐색 결과다. 2015에서 성능 개선 여지는 확인했지만, 임의 PDF에 적용할 안전한 영역 선택, 글자 보호·색/AA 정책, 입력 display list 수명·worker 전달·취소, 배율/DPI/회전/페이지 교체, 메모리 상한, 첫 화면 비용 검증은 제품 구현의 후속 작업이다. 2019는 일반적인 문서 기준으로 유지하고 2015는 이처럼 작은 복합 삽화가 많은 스트레스 사례로 함께 쓰는 편이 유용하다.

## 재현 자료

공개 탐색 도구: `tests/analyze_gpu_scene_complexity.py`. 입력 PDF를 수정하지 않으며 출력 JSON에는 장면 통계·후보 bbox가 들어간다. 개인 문서 결과는 소스에 포함하지 않는다.

```powershell
.venv\Scripts\python.exe -m tests.analyze_gpu_scene_complexity <input.pdf> --output tmp/scene-complexity.json
```

개인 입력의 구체적인 픽셀·실험 스크립트·측정 JSON은 `tmp/gpu-simplify/`에 보관했다. `explore/`는 그룹 경계 후보, `islands/`는 25개 crop 초기 후보, `merged/`와 `confirmation/`은 7개 영역 15회 비교다. 원본 PDF·pickle·BGRA·원본 그림을 포함한 PNG는 커밋하지 않는다. 기본 DLL hash와 `git diff --check`, 탐색 도구 구문·실행 검사를 확인했다.
