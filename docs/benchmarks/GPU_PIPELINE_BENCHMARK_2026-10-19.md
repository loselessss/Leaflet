# GPU 합성 파이프라인 비교 (2026-10-19)

대상: 미배포 1.37.0. 기준은 main `4901da6`에 포함된 네이티브 DLL이며, 최종 구현은 이 작업의 소스와 재빌드한 DLL이다.

## 변경

- GPU 배경 복사에 필요한 Flush/CopyFromBitmap과 최종 EndDraw는 유지한다. 마스크 coverage와 합성 범위 종료에서 중복 제출을 줄인다.
- 마스크 입력의 수명을 적용 범위 종료까지 유지한다. 기존 4개 비트맵 예약과 임시 자원 풀의 상한을 유지한다.
- 비격리 그룹 불투명도 0/1의 불필요한 보간·배경 복사와, 불투명도 1인 혼합 입력의 ColorMatrix를 생략한다.
- 명령당 1 byte의 실행 분류를 생성해 각 정밀 타일에서 반복하던 scope/simple/no-op 해시 검색을 줄인다. 새 결과 캐시는 추가하지 않는다.

## 측정 조건

- Windows, Intel Iris Xe 하드웨어 GPU, PyMuPDF 1.28.2, 1200×900 물리 픽셀, 96 DPI.
- ACB 2019·2015의 첫 페이지를 화면 맞춤·100%·200%로 각각 비교한다. 페이지 중심을 화면 중심에 맞춘다.
- 각 조건에서 3회 준비 후 15회 측정한다. 같은 프로세스에서 기준·변경 DLL을 번갈아 실행하며 순서도 교대한다. 다른 테스트는 동시에 실행하지 않는다.
- 매 회 새 장면 identity를 만들어 페이지·그룹 결과와 이전 정밀 타일을 재사용할 수 없게 한다. 공통으로 준비된 geometry·이미지 업로드 자원은 유지한다.
- 표는 정밀 작업 요청부터 전체 viewport atlas가 준비되어 가져오기 완료될 때까지의 시간이다. 실제 리더와 같은 30ms 간격으로 완료를 확인하므로 확인 대기와 GPU 타일 가져오기 시간이 포함된다. 수 ms의 차이는 확실한 가속으로 해석하지 않는다.
- 최초 PDF 열기·장면 추출·업로드, 입력 안정화 대기 90ms, 화면 Present/vsync는 측정에서 제외한다. 즉 전체 파일 열기 속도나 연속 스크롤 FPS 측정은 아니다.
- 장면 이미지 준비 배율은 1로 고정한다. 확대 화면의 좌표·벡터 합성은 해당 배율로 처리하지만, 확대 후 이미지 해상도 재추출은 이 비교에 포함하지 않는다. ACB 2019의 배율 2 이미지 추출은 기존 64MiB 제한에 걸려, 그 제한을 늘리지 않았다.

## 전체 정밀 화면 완료 시간

단위 ms. 중앙값과 P95는 낮을수록 빠르다. 감소율은 중앙값 기준이다.

| ACB 2019 | 200% | 68.2 | 66.6 | +2.5% | 99.0 | 69.6 |
| ACB 2015 | 화면 맞춤 | 684.3 | 653.6 | +4.5% | 1094.1 | 1319.7 |
| ACB 2015 | 100% | 494.3 | 499.8 | -1.1% | 959.6 | 987.7 |
| ACB 2015 | 200% | 228.7 | 226.7 | +0.9% | 905.4 | 515.1 |

ACB 2019의 100% 완료 중앙값은 이번 측정에서 31.3% 줄었다. 화면 맞춤·200%의 중앙값 차이는 작다. ACB 2015는 뚜렷한 전반적 개선을 확인하지 못했다. 화면 맞춤 중앙값은 4.5% 줄었지만 P95는 늘었고, 100%에서는 첫 정밀 타일이 약 193→252ms로 늦어졌다. 따라서 이 변경을 모든 포스터의 체감 속도 개선으로 설명할 수 없다. 정밀 완료·첫 타일·긴 지연을 구분해서 해석해야 한다.

## 화면 및 회귀 검증

- 각 조건의 첫 출력에서 1200×900 BGRA 전체를 비교했다. 아래 픽셀 차이는 변경 전후의 동일성 검사이며, CPU 렌더와의 모든 색 관리·폰트 재현 정확성을 보장하는 검사는 아니다.

| 문서 | 보기 | 바뀐 픽셀 수 | 최대 채널 차이 (0–255) |
|---|---|---:|---:|
| ACB 2019 | 화면 맞춤 | 0 | 0 |
| ACB 2019 | 100% | 0 | 0 |
| ACB 2019 | 200% | 0 | 0 |
| ACB 2015 | 화면 맞춤 | 0 | 0 |
| ACB 2015 | 100% | 0 | 0 |
| ACB 2015 | 200% | 0 | 0 |

- 화면 맞춤 출력은 이미지로도 검토했다. 글자·도표·사진·마스크 배치에 변경이 보이지 않았다.
- 장면 추출·Direct2D·GPU 합성 관련 테스트 95개 통과. 최종 비트맵 옵션 수정 후 Direct2D/합성 15개 재실행 통과. 네이티브 빌드 `/W4 /WX`와 `git diff --check` 통과.
- 추가 회귀 검사는 비균일·반투명 배경에서 중첩 clip/mask/non-isolated 그룹, 96/120/144/192 DPI, 한 프레임에서 12회 바뀌는 마스크·혼합과 임시 비트맵 덮어쓰기를 다룬다. 배치를 모은 출력과 매 범위마다 명시적으로 제출한 출력도 비교한다.

## 범위와 한계

- 단일 하드웨어에서 한 차례의 교차 측정이다. GPU 클럭·다른 시스템 작업에 따른 반복 편차가 있으며 모든 문서·GPU에 같은 개선율을 보장하지 않는다. P95와 원시 표본을 함께 보아야 한다.
- ACB 2019 장면에는 마스크 23개·그룹 1개, ACB 2015 장면에는 마스크 193개·그룹 3211개가 있다. 이 수는 전체 장면의 입력 규모이며, 각 타일에서 실제 그려진 수가 아니다. GPU timestamp별 작업 시간은 측정하지 않았으므로 이를 특정 GPU 병목의 증거로 단정하지 않는다.
- 배경 복사를 GPU 그리기로 대체하는 후보는 일부 조건에서 빨랐지만 ACB 2015에서 회귀가 나타나 최종 구현에 넣지 않았다. 최종 코드는 기존 GPU 복사를 유지한다.
- 직접 전체 장면을 그리는 진단 경로에서 ACB 2015의 200%는 기준·초기 후보 모두 기존 메모리 제한 오류가 있었다. 최종 비교는 리더가 사용하는 별도 컨텍스트의 정밀 타일 파이프라인으로 수행했다. 그 별도 진단 경로의 오류를 해결했다는 뜻은 아니다.
- 아래 메모리는 두 DLL의 렌더러를 함께 보유한 벤치마크 프로세스의 누적 최대 상주 메모리다. 각 빌드의 앱 메모리 비교가 아니며, VRAM 최고 사용량은 측정하지 않았다. 메모리 절감 효과를 주장하지 않는다.

- ACB 2019까지의 프로세스 peak RSS: 747.4 MiB.
- ACB 2015까지의 프로세스 peak RSS: 1293.6 MiB.

## 재현

```powershell
.venv/Scripts/python.exe -m tests.benchmark_gpu_pipeline <PDF_2019> <PDF_2015> `
  --library baseline=<기준_DLL_경로> --library optimized=native/bin/spdf_d2d_renderer.dll `
  --output tmp/gpu-pipeline-20261019/final-comparison --repeats 15 --poll-ms 30
```
