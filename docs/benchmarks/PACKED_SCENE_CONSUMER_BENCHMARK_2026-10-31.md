# Packed 장면 소비 경로 비교

2026-10-31 · 미배포 1.37.3 유지 · Rust 1·2번 적용 상태

## 구현

worker의 전송용 Pickler가 경로를 가변 길이 float64 바이너리로 기록한다.
수신 측은 PackedCommands로 유지한다. 리더의 경로 중복 확인은 바이너리 키를
사용하고, Rust가 해당 버퍼에서 기존 28바이트 float32 Direct2D 명령 배열을 직접
생성한다. 좌표별 Python float/tuple 복원 및 ctypes 필드 대입을 생략한다.

사각형 클립은 필요한 점만 읽고 여섯 번째 점에서 조기 탈락한다. 이미지 갱신 등
CPU 분석이 필요한 소비자는 호환 iterator를 사용하며 결과를 장면에 캐시하지 않는다.
디스크 저장은 기존 tuple 형식으로 변환하므로 장면 캐시 형식 14와 ABI 24는 유지한다.
확장이 없는 개발 환경의 worker는 기존 pickle을 사용한다. worker 전송은 전과 같이
개인 작업 디렉터리의 임시 파일을 성공적으로 기록한 뒤 교체한다.

PackedCommands는 tuple과의 수치 비교를 지원하지만 hashable하지 않으며,
네이티브 리더만 별도의 bytes 키를 사용한다. 장면 비용 계산은 버퍼 크기를 포함한다.
전송 전에 계산된 기존 _memory_cost가 있는 경우 보수적인 기존 예산을 유지한다.

## 방법

`python -m tests.benchmark_scene_transfer <PDF...> --output <JSON>`

동일한 추출 장면을 입력으로, 기존 pickle과 packed 전달을 번갈아 실행한다.
각 표본은 새 직렬화·복원·GPU 자원/retained scene을 생성한다. 결과 재사용 없음.
워밍업 1회 뒤 각각 7회 중앙값이며 두 번째 실행은 문서 순서를 반대로 했다.
GC는 타이머 밖이다. PDF 추출·프로세스 시작·파일 입출력·최종 그리기는 제외한다.

UI 준비는 역직렬화 + 실제 리더의 GPU 장면 준비를 합친 각 표본의 중앙값이다.
전체 준비는 worker 인코딩부터 UI GPU 장면 생성까지의 각 표본 중앙값이다.
이 수치는 각각 다른 부분별 중앙값을 더해서 계산하지 않았다.

| 실행 | 문서 | UI 준비 기존 → packed | 전체 준비 기존 → packed |
|---|---|---:|---:|
| 1 | ACB 2015 | 268.40 → 205.64ms | 310.88 → 288.13ms |
| 1 | ACB 2019 | 171.91 → 133.70ms | 225.78 → 236.80ms |
| 2 | ACB 2015 | 264.12 → 210.17ms | 311.49 → 285.02ms |
| 2 | ACB 2019 | 185.49 → 146.75ms | 239.29 → 233.39ms |

UI 측 Python 복원·준비는 두 실행 모두 약 20~23% 줄었다. 전체 준비는 2015에서
약 7~8.5% 줄었고, 2019는 실행에 따라 약 5% 증가/2.5% 감소해 안정적인 전체 속도
개선으로 판정하지 않는다. 인코딩은 아직 worker의 기존 Python tuple을 순회한다.
최초 추출부터 packed 형식으로 만드는 단계는 구현하지 않았다.

두 실행 모두 전체 복원 장면과 모든 경로의 네이티브 배열이 기존과 같음을 검사했다.
맞춤·100%·800% 중앙 화면(source scale 1, 1200×900)의 픽셀 해시도 모두 같았다.
테스트는 packed 경로 iterator를 금지한 상태에서도 GPU 배열을 생성할 수 있음을
검사한다. 임의로 손상된 명령 태그·잘린 데이터·개수 불일치는 네이티브 호출 전에 거부한다.
실제 worker·리더·GPU 합성 등 관련 테스트 195개가 통과했다.

프로세스 RSS/VRAM은 별도로 측정하지 않았다. Python 객체 생성 감소를 앱 전체의
메모리 절감 수치로 표현하지 않는다. 원본 PDF·세부 표본은 비공개
`tmp/rust-audit/consumer-results.json`, `consumer-second.json`에 보관한다.
