# 반복 확대 렌더러 개선 비교 (2026-11-07)

Leaflet 1.39.1 개발 중. 기준은 1.39.0 렌더러이며 장면 컴파일러는 양쪽 모두 현재 Rust 경로를 사용한다.

## 적용 내용

1. 정밀 작업자의 D2D 문맥과 장면별 브러시·mesh 연결을 같은 장면·DPI의 다음 작업에 넘긴다. 작업자마다 완료된 장면 하나만 유지한다. 활성 작업과 변경 가능한 브러시를 동시에 공유하지 않는다. 장면 폐기 시 대기·진행 작업을 취소하고 보관 자원을 해제한다. 작업 완료 후 임시 표면·계획 저장소·타일 target은 해제한다.
2. 512·4096·32768 명령 단위의 보수적 범위 색인을 장면 준비 시 만든다. 화면 밖의 완결된 범위를 한 번에 건너뛴다. 범위는 그리기 명령 또는 완결된 scope만 포함하며, 불명확한 상태 전환·마스크 생성/적용 경계·범위를 가로지르는 scope는 묶지 않는다. 배경 복원 장면에는 적용하지 않는다. 타일 계획의 큰 묶음 시작점에서만 검색해 검사 비용을 제한한다.
3. 정밀 작업자의 3입력 마스크 효과 객체를 기존 Flush/EndDraw 이후 재사용한다. 입력 참조를 분리하고 다음 합성에 다시 연결한다. 명령 목록 녹화에는 적용하지 않는다. 이번 단계는 효과 객체 생성 비용을 줄이는 변경이며, 합성 수식·그리기 순서·GPU 제출 횟수를 줄인 변경은 아니다.

압축 RAM 장면 보관 정책은 기존 LFDC/LZ4 경로를 유지한다. 즉시 그릴 GPU 자원은 준비된 상태로, 밀려난 벡터 장면은 RAM 압축 상태로 보관한다. 작업자 보관은 전체 자원을 압축하는 기능이 아니다. 여러 페이지 업로드 분할(후보 4)은 이번 범위에 포함하지 않는다.

## 측정

1200×900, 96 DPI, 하드웨어 GPU. `tests/benchmark_gpu_pipeline.py --rust-scene --repeated-zoom --mode completed --poll-ms 1 --repeats 15`를 사용했다. 각 조건 3회 예열 뒤 15회 측정, DLL 실행 순서를 회전·역순으로 교차한다. 동일 장면을 유지하면서 표본마다 배율을 1.3%씩 증가시켜 이전 픽셀 결과 재사용을 막는다. 각 조건 이름은 시작 배율이며 마지막 측정은 시작의 122.1%다. 요청부터 정밀 atlas 완료·동기 BGRA 읽기·end_frame까지의 중앙값이다. PDF 컴파일·최초 장면 업로드·입력 안정화 대기는 타이머 밖이다. GPU timestamp나 실제 UI 전체 응답 시간이 아니다.

## 추가 비교와 검증

- Python 장면 생성 경로도 별도로 동일 조건에서 비교했다(3회 예열·15회 측정). 이 경로와 실제 Rust 장면 경로를 혼합해 속도 수치를 제시하지 않는다.
- 각 변경을 하나씩 끈 후보도 3회 예열·9회 측정했다. 가장 분명한 이득은 작업자 연결 유지였다. 범위 색인과 효과 객체 재사용의 개별 속도 이득은 조건별로 일관되지 않아 독립적인 단축률을 보장하지 않는다.
- 두 장면 경로 각각 첫·마지막 출력 18개씩, 총 36개 BGRA 화면이 기준과 완전히 일치했다. PDF 원본은 수정하지 않았다.
- 합성 통합 19개, D2D 백엔드 9개, 문서 야간 색상 8개 검사를 통과했다. 긴 마스크 명령 목록을 4096개 이상으로 늘리고 같은 장면의 배율 변경·회전·기울이기·DPI 변경 및 작업 교체를 검사한다.
- 네이티브 빌드는 경고를 오류로 처리하는 기존 빌드 설정으로 성공했다. ABI는 유지한다.

상세 원시 측정·출력과 후보 DLL은 로컬 `.test-runtime/renderer-1391/`에 보관한다.
