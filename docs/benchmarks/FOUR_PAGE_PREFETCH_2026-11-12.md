# 4개 페이지 작업자 병렬 준비 비교 · 2026-11-12

Leaflet 1.39.2 개발 중. 주변 페이지의 벡터 장면 준비를 뷰당 최대 4개의 독립된 Rust 작업자로 동시에 처리한다. 각 작업자는 기존의 페이지 스냅샷 하나를 받아 PDF 해석·벡터/이미지 준비·결과 전송을 마치고 종료한다. 완료된 결과는 기존 RAM 장면 캐시에 설치한다. PDF의 GUI 객체는 작업자 간 공유하지 않으며 스냅샷 추출은 GUI에서 순서대로 수행한다.

## 비교 결과

동일한 논문 PDF의 2~9쪽, 총 8페이지가 RAM에 준비될 때까지의 중앙값(ms). 디스크 장면 캐시 키를 비활성화해 캐시 적중을 배제했다. 작업자 1개와 4개를 번갈아 먼저 실행하고 조건별 첫 1회를 제외한 3회씩을 사용했다. 모든 쌍에서 페이지별 LFSC 벡터 패킷 SHA-256이 일치했다.

| 문서 | 작업자 1개 ms | 작업자 4개 ms | 배속 |
| --- | ---: | ---: | ---: |
| jabc-68-22.pdf | 2544.8 | 972.9 | 2.62× |
| sucato-et-al-2026-urine-sample-for-hpv-detection-in-men-is-it-a-valid-and-non-invasive-diagnostic-alternative.pdf | 2802.2 | 1033.6 | 2.71× |

각 실행에서 실제로 보유한 작업 슬롯의 최대값은 각각 1·4였다. 해당 8페이지의 RAM 장면 크기는 JABC 약 4.29MiB, Sucato 약 2.20MiB로 두 조건에서 같았다.

계측은 첫 작업 요청부터 마지막 RAM 설치까지이며 스냅샷 생성·자식 프로세스 기동·Rust 컴파일·임시 결과 파일 읽기·압축 해제 및 RAM 설치를 포함한다. 첫 페이지 열기와 GPU 업로드·실제 합성·스크롤 입력 지연은 측정하지 않는다. 초기 유휴 대기 180ms도 타이머 밖이다. 조건별 메모리 정책은 1GiB로 고정했고, 실제 앱의 예산이 작으면 동시 작업 수도 줄어든다. 파일 시스템 캐시는 비우지 않았으므로 cold-disk 비교가 아니다. 테스트 두 문서에서의 결과이며 4배 향상을 보장하지 않는다.

## 수명과 메모리 정책

- 첫 유휴 작업은 기존 180ms 대기를 적용한다. 이후 슬롯은 15ms 간격의 별도 이벤트에서 채워 GUI가 페이지 추출 사이에 입력을 처리하도록 한다.
- 작업당 기본 128MiB를 임시 여유로 예약한다. 보유한 Windows 프로세스 핸들로 RSS/PrivateUsage를 샘플링하고 32MiB 여유를 더해 예약량을 올린다. 표본 사이의 순간 최대 사용량을 강제 제한하는 OS 하드캡은 아니다.
- 준비 작업들의 예약 합계는 적응형 장면 예산 이내로 제한한다. hot/압축 RAM 캐시는 별도의 기존 예산을 사용한다. 전체 계획 상한은 장면 예산의 2배 이내이며, 장면 예산은 가용 RAM 등을 기준으로 정해진다. 메모리 압박 시 나중에 시작한 작업부터 정리한다.
- 페이지별 작업자는 전송 압축에 스레드 하나를 사용해 4개 작업자 각각이 압축 스레드를 추가 생성하는 것을 피한다. 완료 결과의 읽기·복원은 기존 백그라운드 읽기 작업자를 사용한다.
- 현재 페이지 작업이 필요하면 선행 준비가 양보한다. 사용자가 이미 준비 중인 페이지로 이동하면 그 작업을 새로 시작하지 않고 현재 페이지 작업으로 승격한다. 문서 수정·닫기·세대 변경·비활성 화면에서는 작업을 취소하고 임시 파일을 정리한다. 결과 읽기가 시작된 경우 읽기 작업자가 파일 정리 책임을 유지한다.
- GPU 자원 업로드는 기존 한 페이지씩 처리하는 경로를 유지한다. 이번 변경은 준비 병렬화이며 합성 백엔드 변경이 아니다.

## 검증

리더 106개, 메모리 정책 5개, 네이티브 작업자 11개 검사 통과. 실제 4개 작업자의 RAM 설치, 4개 제한, 메모리 예약·사용량 증가 시 취소, 현재 페이지 우선 처리·작업 승격, 수정/닫기 정리, 완료 순서가 바뀐 결과의 설치와 화면 불변성을 검사했다. 원시 결과와 실행 스크립트는 로컬 `.test-runtime/prefetch-four/`에 보관한다.
