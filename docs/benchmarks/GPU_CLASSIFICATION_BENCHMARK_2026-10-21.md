# GPU 장면 분류표 제거·제출 경계 후보 비교 (2026-10-21)

기준은 main에 푸시한 77ea7c0 DLL이다. 이번 적용분은 simple/no-op 분류를 기존 명령 byte에 바로 기록해 임시 해시표 4개를 없앤다. 더 공격적으로 GPU 제출 경계와 Blend 합성을 바꾸는 후보도 비교했으나 기본 적용하지 않았다. 앱·설치 프로그램은 미배포 1.37.0, 공개 ABI는 24다.

## 최종 변경

- 이전에는 `prepare_raster_groups`가 simple 시작·종료, no-op 시작·종료를 해시표 4개에 담고, 장면 생성 끝에 다시 replay role byte로 옮겼다. 이후에도 원본 장면에는 해시표가 남았다. worker는 그 내용을 복사하지 않았지만 빈 컨테이너 필드는 가지고 있었다.
- 이제 같은 판정을 할 때 바로 `SimpleOpen`, `SimpleEnd`, `Noop` bit를 기록한다. 기존 `Scope`, `Raster`, 격리 클립 경계 bit와 함께 보관하며, 격리 클립 통합의 simple 제외 조건도 이 byte를 읽는다. 분류표의 중간 생성·해시 삽입·후처리 순회를 없앤다.
- GPU 실행·혼합·Flush/CopyFromBitmap·타일 크기·결과 캐시·출력 픽셀 정책은 바꾸지 않는다. 마스크 build/apply 전환과 단순 범위의 판정 조건도 그대로다.
- 수동 도구에 `--mode scene`을 추가했다. 이미 준비한 경로·이미지를 사용해 새 retained scene을 만드는 시간만 재며, worker 요청·실제 래스터화는 실행하지 않는다. 이 모드는 배율별 중복 측정 대신 문서당 `scene` 조건 하나를 기록한다.

## 메모리 확인

ACB 2015 장면에 있는 분류 항목은 총 16,366개였다. 별도 계측 빌드에서 네 해시표에 같은 형태의 counting allocator를 사용해 `allocate(n)`의 요청 byte를 합산하고 `deallocate(n)`에서 뺐다. 노드·bucket·빈 컨테이너 내부 할당을 포함하고, heap 관리 오버헤드는 포함하지 않는다. 이 계측 빌드의 실행 시간은 성능 표에서 제외한다.

| 장면 하나의 항목 | 77ea7c0 | 최종 |
|---|---:|---:|
| native 명령 수 | 31,302 | 31,302 |
| 해시 분류 항목 | 16,366 | 0 |
| 분류표 allocator 요청량 | 786,096byte | 0 |
| Scene 객체 크기 | 528byte | 272byte |

- 해시표와 장면 객체를 합쳐 원본 장면 하나당 **786,352byte, 약 0.75MiB**를 줄였다. worker는 이전에도 해시 항목을 복사하지 않았으므로 이 수치를 worker 수로 곱하지 않는다. worker의 빈 컨테이너 제거 이득은 위 수치에 추가하지 않았다.
- 직전 [빈 명령 제거](GPU_DIRECT_CLIP_BENCHMARK_2026-10-21.md)의 원본+worker 한 쌍 절감량 885,600byte와 합하면, a8dbd37 대비 같은 쌍의 명령·분류 저장량은 약 **1.59MiB** 줄었다. 이는 해당 컨테이너 저장 공간이며 앱 전체 RSS나 VRAM의 실측 감소량이 아니다.
- 기존 중간 coverage 비트맵 제거는 그대로 유지한다. 이번 최종판이 GPU 비트맵을 추가로 줄인다고 주장하지 않는다. 장면 생성 중에도 네 해시표를 만들지 않으므로 보관 후에만 비우는 방식과 다르다.

## 조건과 측정 범위

- Windows / Intel Iris Xe hardware / PyMuPDF 1.28.2 / 숨김 HWND / 1200×900 물리px / 96 DPI. ACB 2019·2015 첫 페이지, 이미지 준비 배율 1이다.
- 화면 전체 정밀 완료는 새 장면 identity마다 요청부터 atlas 준비·가져오기까지 재며, 완료 확인은 리더와 같은 30ms 간격이다. immutable 경로·이미지 업로드, 최초 PDF 열기·추출, 90ms 입력 안정화, Present/vsync는 제외한다. 결과 재사용을 늘리지 않는다.
- 준비 3회 뒤 측정하고 DLL 실행 순서를 회전·반전한다. 최종 확인은 초기 DLL 준비 순서도 반대로 둔다. 준비 완료 프레임의 BGRA를 따로 비교한다. GPU 측정 중 테스트·빌드·PNG 분석을 병행하지 않는다.
- 장면 생성 모드는 각 문서 준비 3회+측정 25회다. Python 명령 변환과 native 장면 생성이 포함되며, PDF 전체 열기나 연속 스크롤 FPS가 아니다. 최종 정밀 완료는 조건당 준비 3회+측정 15회다. P95는 nearest-rank로 계산한다.
- 절대시간은 시스템/GPU 부하에 크게 달라진다. 과거 441ms와 직접 빼지 않고 같은 회차의 DLL을 비교한다. 분류표 제거가 GPU 작업 수를 줄이는 변경은 아니므로, 화면 완료 시간의 변동과 생성 비용을 구분한다.

## 제외한 GPU 후보

- `batch`: 분류표 제거와 함께 격리 클립 시작의 명시적 Flush를 모두 제거했다. 별도 mask가 없어진 경로에서 같은 context의 SetTarget 순서에 맡긴 후보다. 기존 101개 검사와 ACB 저장 화면 비교를 통과했지만, 첫 비교의 ACB 2015 200% 완료가 561.7→657.7ms로 느려졌다.
- `blend`: batch 후보에 `ID2D1DeviceContext6::BlendImage`를 추가해 eligible 혼합의 별도 backdrop 비트맵·복사·Blend effect를 줄였다. COPY·mask-build·비격리 경로와 미지원 context는 원래 합성으로 처리했다. [Microsoft 문서](https://learn.microsoft.com/en-us/windows/win32/api/d2d1_3/nf-d2d1_3-id2d1devicecontext6-blendimage)는 이 API가 내장 Blend effect와 동등한 결과를 낸다고 설명한다. 기존 101개 검사 및 추가 fallback/제출 검사도 통과했으나, 같은 200%가 714.6ms로 더 느려져 적용하지 않았다.
- blend는 제출 축소에 직접 혼합을 더한 복합 후보다. 위 결과로 BlendImage API만의 비용을 단정하지 않는다. 실제 선택된 직접 혼합 호출 횟수나 GPU pass 수도 계측하지 않았다.
- `small`: Flush 생략을 4,096물리px 이하의 capture로 제한했다. 화면 맞춤에서 기준 523.9ms, 분류표 제거만 468.7ms, 제한 후보 556.6ms였다. 100%·200%에서는 나아졌지만 보기별 방향이 달라 적용하지 않았다.
- 첫 후보 비교는 두 문서 각 보기 준비 3회+측정 15회였다. 제한 후보 비교는 ACB 2015 각 보기 준비 3회+측정 9회다. 이 예비 회차와 최종판 확인을 섞어 하나의 가속률로 제시하지 않는다.

## 검증·한계

- 최종판 관련 테스트 **101개 통과**: gpu_raster 80개, d2d_backend 9개, gpu_composite_integration 12개. 이 중 simple/no-op, 중첩·COPY·mask build/apply·비격리·knockout·혼합·고DPI·취소·worker 복제·분수 좌표·타일 경계 검사를 유지한다.
- 기존 비교의 허용 오차는 완화하지 않았다. 최종판은 출력 정책을 바꾸지 않으며, 후보 비교의 저장 화면도 기준과 같았다. 저장 화면은 조건별 첫 준비 실행(index 0)이고 모든 반복 픽셀·모든 PDF/GPU의 검증은 아니다.
- BlendImage 후보의 추가 검사는 15 혼합 모드×불투명도 3개를 연속 실행하며, source-over 부모의 직접 경로를 COPY 부모의 원래 snapshot 경로와 최대 채널 차이 3 이하로 비교했다. DPI 96/144에서 명시적 readback 경계가 있는/없는 실행도 BGRA 전체가 같았다. 후보와 이 추가 검사는 로컬 실험 자료에 보존하고 최종 적용분에 넣지 않았다.
- C++ /W4 /WX·FXC 엄격 빌드, Python 구문 검사와 git diff --check를 확인한다. GPU timestamp·VRAM 최고 사용량·앱 전체 RSS의 독립 비교는 하지 않았다.
