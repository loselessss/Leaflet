# GPU 타일 계획·선택 자원 준비 비교 — 2026-10-21

개발 버전: 1.37.1 · 공개 ABI: 24 · 비교 기준: 같은 날 완료한 SceneData arena 단계.

## 채택 범위

- 정밀 작업의 각 타일에서 기존 bounds/scope/cull-block 규칙으로 명령 인덱스를 선별한다. PDF 표시 순서, clip/mask 전환과 조상 그룹 의존성은 유지한다. 영향 없는 격리 Normal 캡처만 비울 수 있으며 COPY·knockout·비격리·마스크 아래에서는 보수적으로 유지한다.
- worker는 선별된 명령의 Path/Bitmap/StrokeStyle 래퍼와 mutable gradient brush만 준비한다. 다른 타일은 필요한 미준비 항목을 추가한다. 작업 종료 시 해제하며, 장면 사이의 렌더 결과 캐시는 추가하지 않는다. UI 원본 장면의 binding은 계속 전체를 준비한다.
- 한 작업에 한 타일 계획 버퍼만 보관한다. 입력 명령 1,048,576개·스택 깊이 4096개를 제한하고, 메모리는 선택 명령 수에 맞춰 늘린다. 한도·구조·할당 실패 시 전체 binding과 기존 replay로 돌아간다. 계획은 BeginDraw 전에 만들어 실패한 계획이 그리기 상태를 남기지 않는다. 취소·원본 수명 만료를 준비와 실행 사이에도 확인한다.
- GPU 합성 범위·순서·Flush 경계·벡터 밀도는 바꾸지 않았다. 전용 합성기나 투명 그래디언트 근사는 구현하지 않았다.

## 측정 조건

Intel Iris Xe 하드웨어, 1200×900 viewport, 96 DPI, 두 ACB 포스터의 화면 맞춤·100%·200%. 타이밍은 각 조건 3회 예열 후 15회, DLL 순서를 교차·회전해 측정했다. 매 표본 새 retained scene을 만들어 렌더 결과 재사용을 막았다. 자원 업로드와 최초 장면 생성은 타이머 밖이다.

지표는 정밀 작업 요청부터 전체 atlas 완료·UI import까지다. UI 요청 반환이나 GPU timestamp만의 시간이 아니다. 최종 비교는 5ms polling을 사용해, 이전 실험의 30ms 관측보다 해상도를 높였다. 서로 다른 실행의 절대 시간은 직접 비교하지 않는다. 측정 중 다른 GPU 검사·빌드를 실행하지 않았다.

## 준비 자원과 메모리 범위

별도의 계측 DLL에서 타일 9개×표본 5개(예열 포함)를 기록했다. 아래의 준비 수와 래퍼 payload는 마지막 타일까지 누적된 작업별 값이고, 계획 배열은 그 작업에서 관측한 최대 capacity다. 일반 DLL의 시간 측정과 분리했다.

| 문서 | 보기 | 전체 binding 수 | 준비한 수 | 감소율 | 기준 래퍼 KiB | 최종 래퍼 KiB | 계획 배열 KiB |
|---|---|---:|---:|---:|---:|---:|---:|
| ACB 2019 | 화면 맞춤 | 160 | 160 | 0.0% | 4.38 | 4.38 | 1.27 |
| ACB 2019 | 100% | 160 | 44 | 72.5% | 4.38 | 1.27 | 1.27 |
| ACB 2019 | 200% | 160 | 17 | 89.4% | 4.38 | 0.50 | 1.27 |
| ACB 2015 | 화면 맞춤 | 13,620 | 13,620 | 0.0% | 418.97 | 418.97 | 121.50 |
| ACB 2015 | 100% | 13,620 | 11,056 | 18.8% | 418.97 | 339.97 | 54.00 |
| ACB 2015 | 200% | 13,620 | 4,744 | 65.2% | 418.97 | 144.94 | 24.00 |

래퍼 payload는 sizeof(Path/Bitmap/StrokeStyle)의 합이다. allocator 오버헤드, COM/brush 내부 할당, GPU 자원·RSS·commit·VRAM의 실측이 아니다. 원본 geometry/bitmap 참조는 공유 arena에 남고, dense binding 테이블 자체 크기도 같다. 따라서 준비 개수 감소를 같은 비율의 전체 메모리 감소로 표현하지 않는다.

ACB 2015 200%의 래퍼 payload는 280,608byte 줄지만, 별도 계획 배열과 컴파일 중 임시 스택이 추가된다. 화면 맞춤은 모든 자원을 결국 준비하므로 메모리 절감이 없고 계획 비용이 추가된다. 확대 화면의 준비·작은 래퍼 할당을 줄이는 기반 변경이며, GPU 합성량을 크게 줄이는 단계는 아니다.
