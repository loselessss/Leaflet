# 작은 복합 삽화의 투명 소스 컴파일

측정일: 2026-10-23 · Leaflet 1.37.1 개발 중 · Intel Iris Xe · ABI 24

## 적용한 변경

**작고 복잡한 격리 knockout 삽화를 Python 도형으로 확장하기 전에 투명 이미지 소스로 만드는 경로를 기본 GPU 장면 추출에 적용했다.** ACB 2015에서 장면 항목은 33,260→4,756개로 줄었다. 전체 새 입력 준비 비교에서 PDF 열기·추출·geometry/bitmap upload·장면 구성·그리기·진단 readback의 중앙값은 맞춤 3.06→1.87초였다. 준비된 불변 입력으로 새 정밀 작업을 반복하는 비교에서도 두 실행 모두 개선됐다.

앞선 [영역 단순화 조사](GPU_COMPLEX_REGION_SIMPLIFICATION_2026-10-23.md)의 7개 전체 페이지 crop을 덮는 시제품과 다르다. 이번에는 **삽화 자체의 격리 그룹만 원래 위치에서 투명 배경으로 렌더링**한다. 주변 글자·배경·클립·후속 객체는 기존 GPU 장면에 남는다. 원본 PDF나 저장 결과는 수정하지 않는다. 새로운 페이지/그룹 렌더 결과 캐시는 추가하지 않았다.

작은 삽화의 색과 AA 차이는 남는다. 기존 GPU와 byte 일치를 목표로 한 변경은 아니며, CPU 모드는 그대로 이용할 수 있다. 2019는 후보가 없어 저장한 세 배율 화면이 기준과 byte 단위로 같았다.

## 파이프라인

- `pdfeditor/gpu_regions.py`가 MuPDF device callback을 중계한다. 일반 명령은 원래 `_DisplayListDevice`로 전달한다. 전체 사전 조사나 전체 페이지 display list를 추가로 만들지 않는다.
- isolated=true, knockout=true, Normal, alpha=1, bbox 면적이 페이지의 0.5% 이하인 그룹만 임시 display list 후보로 기록한다. soft mask 생성 중이거나 tile pattern 안에서는 선택하지 않는다.
- callback 128개 미만, live text/텍스트 클립 또는 tile을 포함한 후보는 원래 recorder로 재생한다. 작은 도형이 몇 개뿐인 보통 그룹을 불필요하게 이미지화하지 않는다.
- 복잡한 후보는 **그룹 내부의 원래 색·알파·마스크·knockout**을 MuPDF로 그린 투명 premultiplied RGBA를 얻는다. BGRA로 채널만 바꾸며 alpha를 다시 곱하지 않는다. enclosing clip·부모 그룹·나중에 그린 전경은 기존 순서로 적용한다.
- 기본 이미지 밀도는 요청 raster-scale bucket의 2배이고 가장자리에 source pixel 1개를 추가한다. PDF point 좌표와 원래 그리기 위치를 유지한다. 실제 화면 배율·DPI의 bucket이 커지면 기존 refinement worker가 새 장면을 추출해 삽화 소스를 다시 만든다.
- 생성 픽셀은 `VectorImage`의 일반 불변 입력 자원이 된다. 장면 수명 동안 기존 입력 자원과 같은 방식으로 유지되며, 이전 작업의 완성된 페이지·타일 이미지를 가져오는 최적화가 아니다. 새 추출은 새 픽셀을 만든다. 아래 최초 준비 비교도 매번 새 추출을 수행했다.
- captured image/stencil/mask callback 수를 원래 source index에 반영한다. 이후 원본 이미지의 disk-cache 재구성 ID가 바뀌지 않게 검사했다. 파생 삽화 이미지는 source index가 없는 owned bytes다.
- 새 파생 소스에는 이미지 전용 빠른 재생 recipe가 없어 `can_refine_images`가 false다. zoom refinement는 원본 페이지에서 전체 추출로 돌아간다. live MuPDF 객체를 scene이나 IPC pickle에 남기지 않는다.
- 장면 디스크 형식은 추출 의미 변경에 맞춰 10→11로 올렸다. 공개 native ABI/DLL은 변경하지 않았다.

이는 일반적인 transparency flattening의 완전한 구현이나 PDF 전체를 CPU 이미지로 만드는 경로가 아니다. 선택한 작은 그룹의 source 표현을 바꾸며, 이후 합성은 기존 GPU renderer의 규칙을 따른다. PDF/뷰어 사이 색·AA 차이와 일부 복잡한 knockout 표현 차이를 전부 해소했다고 주장하지 않는다.

## 메모리·실패·취소 상한

- 한 장면에 새 삽화 소스 최대 64개, 합계 **8MiB**. 기존 전체 GPU scene 이미지 64MiB 상한과 함께 계산한다.
- 비용 예상이 한도를 넘는 그룹은 처음부터 원래 벡터 recorder로 전달한다. 최종 크기 검사에서 넘으면 기록한 후보를 원래 명령으로 재생한다.
- 후보 하나의 callback 기록은 65,536개로 제한한다. 초과하면 부분 장면을 게시하지 않고 기존 전체 CPU fallback을 요청한다. 장치/래스터 오류도 정상 완료한 GPU 장면으로 취급하지 않는다.
- recorder의 deadline과 abort cookie를 공유한다. 64 callback마다 시간 제한을 확인하고 원래 append 검사도 유지한다. CPU source 생성 전후에도 확인한다. worker 프로세스의 기존 취소·문서 세대 검사를 유지한다.
- 후보 display list는 추출 중에만 보유하며, 완료/예외/시간 초과에서 device를 닫는다. 줌 결과·다른 페이지를 새로 상주시켜 두지 않는다.

실제 ACB 2015의 한도 점검:

| 요청 raster scale | 컴파일된 그룹 | 새 삽화 소스 bytes | 장면 항목 |
|---|---:|---:|---:|
| 1 | 25 | 193,176 | 4,756 |
| 2 | 25 | 723,904 | 4,756 |
| 8 | 15 | 8,379,296 | 15,822 |

8배에서는 8MiB 상한 때문에 나머지 그룹이 벡터로 남는다. 지원 실패나 품질 밀도 강제 축소 없이 bounded fallback이 동작했다.

## 준비된 장면의 정밀 작업 비교

직전 256슬롯 수명 계획을 포함한 개발 DLL을 양쪽에 사용했다. DLL SHA256은
`8edb5e56aeab510c4c8df410de8f09f09598b367b430d56683920bb6ecdbc336`다.

1200×900 viewport, 96 DPI, source raster scale 1, 맞춤·100%·200%. 매 표본 새 retained scene과 새 sharp job을 만들었다. PDF 추출·불변 geometry/bitmap upload·retained scene 생성은 타이머 밖이고 request→sharp atlas 완료가 안이다. 즉 CPU 삽화 컴파일 시간이 이 표 안에 있는 것은 아니다. 기존 공개 `tests.benchmark_gpu_pipeline`과 같은 sharp 완료 지표이며, 이전 7개 crop 실험의 CPU 준비·readback까지 합친 지표와 직접 비교하지 않는다.

조건마다 3회 예열 후 15회 측정하고 두 lane 순서를 교차·회전했다. 다른 GPU 검사·빌드를 동시에 실행하지 않았다. 단위 ms, 양의 %는 단축이다.

## 새 PDF부터 정밀 화면까지

삽화 컴파일 비용을 숨기지 않기 위해 **PDF 열기→추출→전체 geometry/bitmap upload→새 retained scene→sharp 완료→진단 readback/프레임 종료**를 모두 시간 안에 넣었다. 각 표본 이전 자원과 입력을 해제하고 MuPDF store를 비웠다. 양쪽 Qt/window/device 시작 비용, 앱 시작·CPU preview·worker 프로세스 시작/IPC는 제외했다. 따라서 앱을 켜서 첫 preview를 보는 시간 자체는 아니다.

맞춤 화면, 각 문서/방식 1회 예열 후 7회, 순서 교차. 모든 입력과 삽화 소스는 표본마다 새로 만들었다. 각 열은 단계별 중앙값이므로 합이 전체 중앙값과 같지는 않다. 단위 ms.

| 문서·방식 | 전체 | 추출 | 불변 자원 upload | 새 scene 구성 | sharp 완료 |
|---|---:|---:|---:|---:|---:|
| 2015 기준 | 3060.97 | 1748.08 | 843.11 | 140.21 | 216.57 |
| 2015 삽화 소스 | 1867.43 | 1274.89 | 428.92 | 18.11 | 27.33 |
| 2019 기준 | 1360.15 | 1013.58 | 276.88 | 2.27 | 24.97 |
| 2019 삽화 소스 | 1366.44 | 1013.80 | 284.11 | 1.86 | 23.63 |

2015는 약 **39.0% 단축**, 2019는 약 **0.5% 차이**다. 장면 항목 감소율만큼 추출 전체가 줄지는 않았다. 남은 글자 outline·원본 이미지 준비와 문서 해석 비용도 크다.

## 별도 프로세스 메모리 관찰

각 문서/방식을 독립 프로세스에서 새 추출·upload한 다음 새 scene으로 세 배율을 한 번씩 그렸다. 여러 lane을 함께 띄운 시간 측정의 최고값을 메모리 효과로 사용하지 않았다. 아래는 2015 재실행과 2019 첫 관찰이다. 구성별 프로세스 하나의 진단이므로 통계적 보장은 아니다. MiB.

| 문서·방식 | peak RSS | peak commit | 현재 RSS |
|---|---:|---:|---:|
| 2015 기준 | 553.64 | 590.06 | 485.97 |
| 2015 삽화 소스 | 393.62 | 433.61 | 333.82 |
| 2019 기준 | 582.84 | 658.29 | 553.98 |
| 2019 삽화 소스 | 581.16 | 654.73 | 552.36 |

2015의 peak RSS는 약 **160.0MiB**, peak commit은 약 **156.4MiB** 낮았다. 최초 별도 실행에서도 감소가 관찰됐지만 이 표는 보존한 재실행 JSON을 기준으로 한다. VRAM만의 측정은 아니며 Python·MuPDF·Qt·native resource·driver 등을 포함한다.

기존 `_gpu_scene_cost`의 Python 장면 비용 추정은 48,928,646→28,130,813bytes(약 46.66→26.83MiB)였다. 이미지 픽셀 bytes 합은 3,249,064→3,178,120bytes였다. 이는 구조/논리 비용이며 RSS 절감값과 같은 종류의 수치가 아니다.

## 화면과 검사

저장한 ACB 2015 세 배율의 기준 대비 차이:

| 배율 | 다른 픽셀 | 화면 비율 | 최대 채널 차이 | 전체 BGRA 평균 절대 차이 |
|---|---:|---:|---:|---:|
| 맞춤 | 950 | 0.088% | 207 | 0.0213 |
| 100% | 2,019 | 0.187% | 177 | 0.0342 |
| 200% | 4,186 | 0.388% | 171 | 0.0556 |

전체 화면과 확대 삽화 crop을 시각 확인했다. 이전 전체 페이지 crop 후보보다 차이 픽셀 수는 줄었고 주변 글자·선의 번짐을 피했다. **작은 삽화의 색은 여전히 눈에 띄게 밝아지는 부분이 있다.** 최대 차이가 작다고 하지 않는다. 2019 세 화면은 기준과 byte 일치했다. 시간 비교 두 실행 사이 후보의 저장 화면 재현 여부는 개인 quality JSON에 기록했다.

- 관련 GPU 추출·색·합성·새 삽화·scene disk cache 검사 **122개 통과**.
- 새 검사에서 premultiplied alpha 0.5를 다시 곱하지 않는지, 투명 padding, 배경/전경 순서, 외부 clip, live text 보호, 마스크 생성 보호, 후보 거절 원본 재생, byte/operation/time 한도, 회전·zoom 재추출, pickle와 worker 전달, captured image 뒤 원본 image ID·disk 재구성을 확인했다.
- 기존 worker 입력 검사 중 수정/복원/암호화/링크 실패 fallback **4개 통과**. 링크 성공을 요구하는 별도 1개는 현재 실행 환경에서 `os.link`가 PermissionError(13)를 내므로 실패했다. 새 추출 전 page 번호 검사에서 발생하며 원본 보존 export fallback은 정상이다. 이 권한 문제를 렌더링 변경으로 고치거나 숨기지 않았다.
- 기본 native DLL hash 유지, Python syntax/import 검사, diff 공백 검사 확인. 전체 데스크톱 수동 조작·장치 reset·다중 모니터를 새로 모두 검증한 것은 아니다.

푸시 전 후속 검증에서는 파일 링크를 허용하는 실행 환경에서 GPU·scene memory·backend·릴리스 패키징·릴리스 노트·worker 입력 검사를 함께 실행해 **165개 모두 통과**했다. 위에서 실패했던 링크 성공 검사도 이 실행에서는 통과해, 해당 실패가 기존 샌드박스의 권한 제약임을 확인했다.

## 재현 자료

구현: `pdfeditor/gpu_regions.py`, `pdfeditor/gpu_raster.py`. 비교용 `simplify_regions=False`는 내부 Python 추출 호출에서만 사용한다. CPU 보기 모드는 변경하지 않았다. 일반 분석 도구 `tests/analyze_gpu_scene_complexity.py`는 기본으로 단순화 전을 분석하며 `--compiled`로 적용 후를 볼 수 있다.

입력 원본, baseline/candidate scene pickle, shader가 아닌 Python 실험·CPU 변환 자료, BGRA/PNG, 통계는 개인 `tmp/gpu-regions-integrated/`에 보관한다. `timing/`·`confirmation/`은 15회 비교, `cold/`는 7회 전체 준비 비교, `memory/`는 독립 프로세스, `limits.json`은 8배 한도 검사다. 원본 문서·그림을 저장한 파일은 소스에 포함하지 않는다.
