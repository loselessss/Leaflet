# 정밀 GPU 작업 준비·범위 인덱스 비교 (2026-10-20)

기준은 main의 67f8ecb(격리 그룹·단일 클립 통합 포함)이며, 앱·설치 프로그램은 미배포 1.37.0이다. 이번 변경은 UI에서 정밀 작업을 준비하는 복사와 타일별 그룹 범위 검색을 줄인다. 렌더 결과 재사용을 늘리지 않는다.

## 변경

- 유효 그룹의 종료 위치·경계를 packed 배열에 담고, 명령 위치별 uint32 인덱스로 접근한다. 기존 unordered_map의 노드 복사를 연속 배열 복사로 바꾸고 정밀 replay의 범위 해시 검색을 없앤다.
- 그룹 경계 계산·유효성·명령 순서·화면 밖 제외·마스크 build/apply 경계·클립 통합 조건은 유지한다. 인덱스가 없는 명령은 UINT32_MAX로 표시한다. 공개 네이티브 ABI는 24다.
- simple_scopes/simple_ends/noop_scopes/noop_ends는 장면 생성 시 실행 분류 byte에 반영된 뒤 worker에서 읽지 않는다. worker 복제에서 이 네 해시 집합의 복사를 제거한다. immutable 자원 소유권과 기존 취소 처리는 유지한다.
- 이는 UI 요청 준비와 replay의 CPU 작업을 줄이는 변경이다. UI에서 준비하는 모든 작업을 worker로 옮긴 것이 아니며, 새 worker·픽셀 캐시·렌더 해상도 변경도 없다. 총 GPU 메모리 감소를 실측한 결과는 아니다.

## 비교 조건

- Windows / Intel Iris Xe hardware / PyMuPDF 1.28.2 / 숨김 HWND / 1200×900 물리px / 96 DPI. ACB 2019·2015 첫 페이지를 화면 맞춤·100%·200%로 비교하며 이미지 준비 배율은 1이다.
- 매 표본 새 장면 identity를 만들고 geometry·이미지 업로드는 타이머 밖에서 준비한다. 기준/후보를 번갈아 실행하며 순서를 교대한다. GPU 테스트·빌드를 측정과 병행하지 않는다.
- **요청 전용:** 준비 3회 + 측정 31회, 두 회차. request_sharp_scene 호출부터 반환까지를 재고 타이머 밖에서 즉시 취소한다. 완료 확인이나 픽셀 readback은 하지 않는다. 실제 worker queue를 사용하므로 worker 시작과 자원 경합은 발생할 수 있다. UI 입력→Present 지연을 측정한 값은 아니다.
- 요청 전용 첫 회차는 같은 소스의 private dense DLL로 측정했다. 두 번째 회차는 통상 빌드한 추적 대상 DLL로, 준비 순서를 뒤집어 확인한다. 타이머 밖 취소 대기 25ms와 다음 표본 앞 25ms 대기는 동일하다.
- **전체 완료:** 준비 3회 + 측정 15회, 준비 순서를 뒤집은 두 회차. 기존 512px 타일·2px gutter와 30ms 완료 확인 간격을 유지한다. 정밀 요청부터 viewport atlas 준비·가져오기 완료까지이며, 최초 파일 열기·장면 추출·업로드·90ms 입력 안정화·Present/vsync는 제외한다.
- 절대시간은 시스템/GPU 상태에 따라 달라 같은 회차의 두 DLL을 비교한다. P95는 nearest-rank 값이다. 요청 준비의 몇 ms 절감과 화면 전체 완료시간의 수백 ms를 혼동하지 않는다.

요청 전용 비교에서 ACB 2015의 중앙값은 두 회차·세 보기 모두 줄어 감소율은 14.2~27.6%다. 이는 UI 요청 준비 구간의 개선율이며, 화면 완성 시간이 같은 비율로 줄었다는 뜻은 아니다.

## 제외한 합성 후보

다음은 별도의 준비 3회 + 측정 7회 예비 비교다. 기준은 역시 67f8ecb다. 두 후보 모두 GPU 관련 테스트 19개를 통과했지만, 화면 맞춤/100% 성능 때문에 채택하지 않았다.

| 후보 | ACB 2015 화면 맞춤 | 100% | 200% | 판단 |
|---|---:|---:|---:|---|
| 통합 격리 클립의 시작 Flush 제거 | 407.89→466.75ms | 411.57→412.60ms | 251.80→225.17ms | 화면 맞춤 약 14% 악화. 제출 감소가 실제 지연 감소로 이어지지 않아 제외 |
| clip layer+흰 사각형을 직접 geometry fill로 대체 | 407.89→525.85ms | 411.57→443.09ms | 251.80→228.76ms | 화면 맞춤 약 29%, 100% 약 8% 악화해 제외 |

- 시작 Flush 제거는 저장한 두 문서 여섯 화면에서 BGRA 차이가 없었다. 직접 fill은 최대 채널 차이 2, alpha 차이 0이었다. 픽셀 차이만으로 제외한 것이 아니라 성능 결과를 반영했다.
- 최종 코드는 기존 mask rasterizer와 시작 Flush를 유지한다. 이전 셰이더의 UNORM8 반올림과 backdrop 복사도 그대로다.

## 회귀 검사·한계

- 최종 관련 테스트 99개 통과: gpu_raster 80개, d2d_backend 9개, gpu_composite_integration 10개. 기존 화면 밖 명령 묶음, 부분 범위, 마스크 전환, 중첩 blend/clip, 회전·반사·shear·고DPI, 취소와 원본 장면 닫기를 포함한다.
- C++ /W4 /WX 및 FXC ps_4_0 /Gis 빌드, Python 구문 검사와 git diff --check를 통과했다. 앱·설치 프로그램 1.37.0 및 공개 ABI 24를 유지한다.
- GPU timestamp·VRAM 최고 사용량·연속 스크롤 FPS는 측정하지 않았다. 프로세스 RSS/commit은 두 DLL을 함께 가진 상태이므로 DLL별 메모리 비교로 보지 않는다.
- 전체 완료 표본의 저장 화면은 조건별 첫 준비 실행(index 0)이다. 12쌍의 BGRA가 모두 일치했고 두 문서의 화면 맞춤 PNG도 확인했다. 모든 측정 반복 표본의 픽셀을 검사한 결과나 모든 PDF의 품질 보장은 아니다.
