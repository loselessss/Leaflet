# 벡터 자원 재사용·투명도 그룹 비교

2026-11-05, 개발 버전 1.38.0. 렌더러 ABI 26, MuPDF 입력 ABI 3,
장면 저장 의미 버전 23. 개인 PDF·화면·원시 측정은 비공개 검증 폴더에 보관한다.

## 최근 페이지의 벡터와 GPU 자원

이전에는 인접 준비 범위를 벗어나면 이미 방문한 페이지의 네이티브 장면까지
폐기했다. PDF를 다시 해석하지 않더라도 도형·글꼴의 GPU 자원을 다시 만들었다.
변경 후에는 유효한 최근 장면을 LRU로 유지하고, 문서 수정·메모리 부족·닫기에서
회수한다. 캐시 대상은 컴파일된 벡터 장면과 그리기 자원이며, 페이지 이미지
캐시를 확대하는 변경은 아니다. PDF 원본에 들어 있는 사진 등의 픽셀 데이터와
기존의 표시용 미리보기·정밀 합성 캐시는 별도로 남는다.

RAM 예산은 총량의 1/16·가용량의 1/4·2GiB 중 작은 값이다(최소 16MiB).
보기 → 화면 렌더러에서 자동/256/512/1024/2048MB 상한을 설정한다.
GPU 자원은 RAM 예산의 절반·DXGI 프로세스 예산의 1/4·GPU 여유량의 절반으로
추가 제한한다. 현재 페이지를 보호하며 비활성 네이티브 장면은 최대 128쪽이다.
이는 프로세스 전체 RSS나 실제 VRAM 사용량의 고정 상한이라는 뜻은 아니다.

인접 2~8쪽을 180ms의 대기 시간 뒤 한 쪽씩 준비한다. 스크롤 중 진행 중인
준비를 취소하지 않고, 해당 쪽으로 진입하면 같은 작업을 전경으로 승격한다.
작은 준비 장면은 한 대기 주기마다 최대 한 쪽의 GPU 자원까지 생성한다.
큰 포스터 업로드는 첫 표시 때 수행해 사전 준비 때문에 GUI가 오래 멈추지
않도록 한다. 가용 RAM이 1GiB 미만이면 사전 준비를 중단한다.

논문 형태의 시험 PDF 12쪽(각 48줄), 1→9→1쪽 이동 비교:

| 항목 | 이전 | 이후 |
| --- | ---: | ---: |
| 돌아온 페이지의 GPU 자원 준비 | 72.103ms | 0.007ms |
| 이동 1회당 장면 업로드 횟수 | 3 | 2 |
| 최종 픽셀 | 기준 | 동일 |

같은 컴파일 장면·같은 DLL에서 이전 폐기 정책과 새 정책만 비교했다.
새 장치를 사용하고 워밍업 1회 제외 후 순서를 번갈아 3회 측정한 중앙값이다.
시간은 네이티브 자원 조회/생성 단계만이며 전체 페이지 전환 지연이 아니다.
GPU 프레임은 직접 벡터 그리기로 생성했고 페이지 이미지 재사용은 하지 않았다.

## 더모아젠의 그라데이션 투명도

사용자가 지적한 1쪽 삽화에는 약 1,160개 음영과 945개 투명도 그룹이 겹친다.
그라데이션 하나의 불투명도를 조절하기 위해 임시 합성을 반복하는 Normal 그룹을
그라데이션 색상 정지점의 알파로 합쳤다. 여러 그리기가 겹치는 그룹·마스크·
직접적인 knockout 대상은 유지한다. knockout과 소스를 분리하는 기존 격리 clip
표면도 유지한다. 새 래스터 소스를 만들지 않는다.

1200×900, 워밍업 1회+교대 3회 중앙값. 업로드 제외, 정밀 GPU 완료와 readback 포함.

| 조건 | 명령 이전→이후 | GPU 완료 ms 이전→이후 | 기존 GPU 대비 평균 RGB 차이 / 255 |
| --- | ---: | ---: | ---: |
| 더모아젠 맞춤 | 10433→9323 | 548.6→483.3 | 0.0757 |
| 삽화 전체(400%) | 10339→9229 | 510.8→474.7 | 1.3901 |
| 삽화 중심(800%) | 10255→9147 | 518.6→481.0 | 4.4569 |
| 삽화 중심(3200%) | 1953→1879 | 286.2→271.0 | 0 |
| ACB 2015 맞춤 | 4714→4714 | 62.0→61.4 | 0 |
| ACB 2019 맞춤 | 331→331 | 57.1→58.1 | 0 |

800% 화면에서 기존 GPU와의 평균 채널 차이는 1.75%지만, 최대 차이는
171/255이고 채널 차이가 16을 넘는 픽셀이 9.1351%다. 변화는 구슬의 색·
하이라이트 등에 집중된다. 이 수치를 모든 픽셀의 색차가 10% 이내라는 뜻으로
해석하지 않는다. 평균 RGB 절대차는 지각 색차(ΔE) 지표도 아니다.

기존 GPU와의 차이만 보고 후보를 처음 제외했으나, 같은 영역의 CPU 기준을
추가 확인한 결과 후보가 오히려 원본에 가까웠다.

| 800% 화면의 CPU 대비 오차 | 기존 GPU | 후보 GPU |
| --- | ---: | ---: |
| 평균 RGB 절대차 / 255 | 7.4144 | 3.8331 |
| 채널 차이 16 초과 픽셀 | 17.702% | 11.827% |

사용자가 표현 차이보다 속도를 우선하도록 명시했고, 이 영역은 속도와 CPU
기준의 평균 오차가 함께 개선되어 채택했다. CPU 모드·저장·인쇄 결과는 바꾸지 않는다.
일반 그룹·마스크·배경 의존 효과까지 동일하게 단순화할 수 있다는 의미는 아니다.

## 실행 항목과 확인

- 전체 자동 회귀 검사 878개 통과. 단일 그라데이션·겹침·마스크·knockout,
  캐시 재방문·문서 수정·VRAM 부족·사전 준비 승격과 UI 시작 경로를 포함한다.
- GitHub 설치본의 두 바로가기가 같은 `sPDF.Desktop` ID를 써서 시작 메뉴에는
  편집기 하나만 나타나는 것을 확인했다. 읽기는 기존 ID를 유지하고 편집기는
  `sPDF.Desktop.Editor`로 구분한다. 바탕 화면 바로가기는 한 선택 항목으로 둘을 만든다.
- 공식 스토어판 1.37.5.0을 확인용 PC에 설치했다. 기존 등록 항목은 `sPDF`
  하나이며 읽기 모드로 실행되었다. 새 매니페스트는 기존 `sPDF` ID를 유지하고
  `LeafletEditor` 항목을 추가한다. 같은 실행 파일에 서로 다른 실행 인수를 전달한다.
- 첫 화면은 읽기/편집 모드를 표시한다. 밝은 모드·다크 모드의 두 창을 확인했다.
- MSIX의 실행 인수는 [Application 매니페스트](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-f-application)의 `uap10:Parameters`를 사용한다.
  해당 속성을 무시하는 환경에서도 [프로세스 앱 ID](https://learn.microsoft.com/en-us/windows/win32/api/appmodel/nf-appmodel-getcurrentapplicationusermodelid)로 모드를 구분한다.
  기존 패키지 ID·읽기 앱 ID·파일 연결 ID·Windows 최소 버전은 유지한다.
- 최신 실행 파일·설치 파일·스토어용 MSIX 빌드가 성공했다. 소스/실행 파일의
  GPU 장면과 실제 프레임을 15조건에서 대조했고, 별도 문서 45쪽도 모두 GPU로 표시했다.
- 확인용 PC의 GitHub 설치본을 1.38.0 개발본으로 갱신했다. 시작 메뉴와 바탕 화면의
  두 바로가기 인수·앱 ID를 읽어 확인했고, Windows 시작 목록에도 둘이 따로 나타났다.
  기존 공식 스토어판 1.37.5는 별도로 유지한다. 새 MSIX는 Windows SDK 검증을 통과했으며
  스토어 게시·업데이트나 새 MSIX의 설치 검증을 수행했다는 의미는 아니다.
- 개발 GUI에서 첫 화면의 두 모드를 밝은/어두운 테마로 확인했다. 공식 스토어 앱의
  직접 화면 캡처는 Computer Use 앱 접근 승인 시간 초과로 완료하지 못했으며,
  해당 설치본의 패키지 등록 정보와 실행 창 제목으로 읽기 모드 실행을 확인했다.
