# 추출 후 독립 이미지 버퍼의 Rust 병렬 처리

2026-10-31 · 미배포 1.37.3 유지

## 구현

PDF 문서를 닫은 뒤, 최종 이미지 bytes만 대상으로 전송 준비를 병렬 처리한다.
MuPDF/Qt/Python 객체를 작업 스레드에서 호출하지 않는다. Python bytes의 강한 참조를
호출 중 유지하고 immutable 슬라이스만 Rust에 빌려준다. GIL을 해제한 동안 Rust의
scoped thread가 1MiB 독립 블록을 LZ4로 무손실 압축한다. 입력 복사는 없다.
기본 실행자는 호출 스레드를 포함해 2개이며, 실제 CPU 수에 맞춰 줄인다. 도구 API는
최대 4개로 제한하고 스레드 생성 실패 시 이미 있는 실행자들이 남은 작업을 처리한다.
작업이 끝나면 모든 스레드를 join하고 원래 이미지 순서로 결과를 묶는다.

원본 이미지 버퍼의 내용·알파·그리기 순서는 바뀌지 않는다. 수신 시 Rust가 원래
bytes를 복원하며, 같은 소스의 여러 참조는 기존처럼 같은 객체를 공유한다.
디스크 캐시 형식과 렌더러 ABI는 유지한다. 이 단계는 재사용 캐시가 아니다.

- 64KiB 이상 이미지의 합이 8MiB 이상일 때만 수행한다.
- 중복 소스는 identity로 제거하고 입력 합계 64MiB를 넘기지 않는다.
- packet이 원본의 90% 이하로 줄지 않으면 원본을 보낸다.
- decode는 원본 길이 64MiB, 블록 길이 1MiB 및 모든 입력/출력 경계를 검증한다.
- `lz4_flex=0.14.0`을 고정하고 safe-encode/safe-decode/checked-decode를 유지한다.
  crate 원본/체크섬/고지는 기존 Cargo legal 수집 경로에 자동 포함한다.
- 기존 개발 환경에 확장이 없거나 작은 작업이면 기존 직렬 전송 경로를 유지한다.

실제 worker CLI의 `--transfer-workers`는 0(기존), 1(직렬 압축), 2(기본), 4를 지원한다.
UI 설정은 추가하지 않았다. Python 장면/좌표 전송 준비와 MuPDF 추출 자체는 이
병렬 단계의 대상이 아니다.

## 비교

`python -m tests.benchmark_parallel_buffers <PDF...> --output <JSON>`

같은 추출 결과를 입력으로 매번 새 전송 준비/직렬화/복원/GPU 자원을 만든다.
raw·Rust 1스레드·Rust 2스레드 순서를 회전하며 워밍업 1회 후 각 7회 중앙값이다.
두 번째 실행은 문서 순서를 반대로 했다. 타이머는 추출 **후** 전달 준비부터 GPU
장면 생성까지다. PDF 추출·파일 입출력·프로세스 시작·최종 그리기는 제외한다.

| 실행 | ACB 2019: 기존 | Rust 1스레드 | Rust 2스레드 |
|---|---:|---:|---:|
| 1 | 279.66ms | 258.56ms | 242.48ms |
| 2 | 233.35ms | 214.87ms | 199.01ms |

기존 대비 해당 구간은 약 13~15%, 같은 압축 알고리즘의 1스레드 대비 약 6~7% 단축됐다.
2019의 파일 크기는 27,891,634→7,828,897 bytes였다. 최종 수신/복원은 기존보다
느릴 수 있다(두 번째 실행의 복원 중앙값 10.65→26.47ms). 이는 전체 후처리 구간의
개선과 구분한다. UI 전체 지연 또는 PDF 열기 전체의 13~15% 개선을 뜻하지 않는다.

첫 실험의 2MiB 기준에서는 ACB 2015가 약 305→306ms로 이득이 없었다. 최종 기준을
8MiB로 조정했고 2015의 대상 소스 약 2.76MB는 우회한다. 두 번째 비교에서 2015의
각 모드 결과 파일은 같은 7,802,536 bytes였으며, 약 309~321ms의 차이는 같은 전송
경로에서의 시간 편차로 본다. 병렬화 이득으로 주장하지 않는다.

두 문서의 전체 장면 bytes와 맞춤·100%·800%(source scale 1, 1200×900) 픽셀 해시가
세 방식 모두 일치했다. 1·2·4스레드의 압축 packet도 deterministic하게 일치했다.

## 실제 worker와 메모리 관찰

별도 새 프로세스에서 실제 worker를 각 모드 3회 실행한 진단 중앙값:

| 문서 | 기존 peak RSS | 2스레드 peak RSS | 기존 worker 경과 → 후보 |
|---|---:|---:|---:|
| ACB 2015 | 99.47MiB | 99.17MiB | 1,441.83 → 1,508.09ms |
| ACB 2019 | 248.36MiB | 252.00MiB | 1,016.35 → 1,036.22ms |

worker 경과는 추출·장면 비용 계산·파일 기록도 포함하며 수신/GPU 준비는 제외한다.
3회 관찰만으로 전체 worker 속도 개선을 주장하지 않는다. 전송 크기는 작아지지만
peak RSS 감소는 확인되지 않았고 2019는 약 3.6MiB 높았다. 별도 VRAM 측정은 없다.

직렬/병렬 무손실·공유 참조·노이즈 원본 우회·작은 작업 우회·스레드 수/메모리 상한·
손상 packet을 검사했다. 관련 추출/worker/리더/GPU 합성/배포 테스트 270개가 통과했다.
개인 PDF·원자료는 `tmp/rust-audit/parallel-buffers-{first,second}.json`,
`parallel-memory.json`에 보관한다.
