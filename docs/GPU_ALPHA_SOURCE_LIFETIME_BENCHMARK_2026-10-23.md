# 알파 중간 소스의 수명 단축 비교

측정일: 2026-10-23 · Leaflet 1.37.1 개발 중 · Intel Iris Xe · native ABI 24

## 결과와 채택

**색 이미지·마스크의 결합이 끝날 때 중간 소스를 해제하는 경로를 기본 적용했다.** [앞선 알파 결합](GPU_ALPHA_IMAGE_FUSION_BENCHMARK_2026-10-23.md)의 출력 표현은 유지하면서, 전체 페이지 추출 뒤까지 원본 BGRA 쌍을 모두 보관하는 기간을 없앴다. 결과 캐시 재사용이나 메모리 한도 증가는 아니다.

- ACB 2019 source bucket 1의 장면과 세 배율 GPU 화면은 이전 결과와 byte 일치했다. 장면 277개 항목과 최종 픽셀 bytes 합계 25,006,444도 같다.
- ACB 2019 source bucket 2는 이전에는 추출 중 64MiB 한도로 실패했지만, 새 경로는 동일한 한도에서 성공한다. 최종 픽셀 bytes 합계는 59,270,664bytes(약 56.52MiB), 항목 수는 277개다. 이 해상도의 새 준비된 GPU 장면도 맞춤 약 25ms, 100~200% 약 18ms에 그렸다.
- 별도 추출·직렬화 프로세스를 각각 새로 시작한 3회 peak RSS 중앙값은 320.61→308.19MiB, 약 12.42MiB 줄었다. 준비 완료 뒤 RSS는 거의 같았다. source bucket 2의 더 큰 최종 자원은 bucket 1보다 메모리를 더 쓴다.
- ACB 2015는 보간이 다른 마스크를 그대로 유지한다. source bucket 1·2의 장면 내용은 이전과 같다. 이번 단계의 별도 그리기 개선을 주장하지 않는다.

초기 준비 시간은 참고 지표로 계속 기록하고, 채택 판단에서는 준비 후 그리기·메모리·화질을 우선한다는 사용자 기준을 반영했다. 동일 source bucket의 추가 화질 손실은 없다. 알파 사전 결합 자체의 경계 차이는 앞선 단계와 동일하다.

## 구현과 한도

1. 원래 이미지·마스크 callback으로 추출하고 `pop_clip`에서 완성된 5항목 범위를 확인한다. 앞선 단계와 같은 일반 알파·빈 transfer·동일 크기/변환/보간 조건만 선택한다. 여러 객체가 있는 범위나 서로 다른 보간은 유지한다.
2. `gpu_alpha.AlphaSourceTracker`가 이 추출 작업 안에서만 이미지 bytes의 참조 수와 원본 저장소의 key를 추적한다. pixels를 추가로 보관하지 않으며 최초 후보가 생길 때 인덱스를 만든다. 이후 추가·tile 복제/제거도 반영해 페이지 전체 명령을 매번 재검색하지 않는다.
3. 같은 bytes를 다른 명령이 계속 쓰면 해당 원본을 유지하고 비용도 계속 계산한다. 참조가 없어진 색·마스크 입력만 작업 내 이미지 저장소에서 해제한다. 파생 BGRA와 사각형 clip, 원래 opacity·두 원본 callback refresh recipe는 앞선 단계와 같다.
4. 최종/추출 중 이미지 데이터 예산은 기존 64MiB다. 누적 파생 픽셀 생성 예산도 기존 64MiB를 유지한다. 결합 전후의 작업용 복사까지 모두 합한 프로세스 RSS가 64MiB라는 의미는 아니다. 이미지를 결합하는 순간의 임시 복사와 MuPDF 원본 decode/store는 별도다.
5. 후처리에서 새로 단순화된 범위도 마지막 일괄 결합 단계로 처리하되, 이미 생성한 파생 소스와 같은 누적 생성 예산을 공유한다. 시간 초과는 기존 작업 취소/fallback을 따르고 후보 변환 실패 시 원래 범위를 유지한다.
6. 이미지 전용 확대 갱신이 원본 쌍을 모두 읽다 한도에 걸리면 `None`을 반환하고 기존 worker가 전체 추출을 수행한다. 전체 추출에서는 범위별로 중간 소스를 해제하므로 더 높은 bucket도 성공할 수 있다. 작업의 남은 timeout은 기존 worker 규칙대로 전달한다.

장면 디스크 형식은 새 지원 범위를 반영해 12→13으로 변경했다. 앱과 설치 프로그램은 미배포 **1.37.1**, native DLL/ABI는 그대로다. 기존의 CPU 화면 표시 후 GPU 준비 완료 시 전환하는 흐름과 편집/저장은 변경하지 않았다.

## 메모리: 추출 작업 프로세스

동일 PDF를 새 프로세스에서 열고 전체 추출→장면 비용 계산→pickle 전송 파일 생성까지 수행했다. GUI·GPU 렌더 자원은 생성하지 않았다. 후보별 독립 프로세스 각 3회다. 과거 문서의 준비된 pickle 입력만 읽어 GPU로 그린 측정과 합산하지 않는다.

| ACB 2019 | 기존 일괄 결합 bucket 1 | 범위별 결합 bucket 1 | 범위별 결합 bucket 2 |
|---|---:|---:|---:|
| peak RSS 중앙값 | 320.61MiB | 308.19MiB | 340.32MiB |
| peak commit 중앙값 | 351.56MiB | 338.34MiB | 370.76MiB |
| 완료 후 RSS 중앙값 | 277.84MiB | 278.42MiB | 310.88MiB |
| 추출·전송 파일 생성 중앙값 | 1,380.41ms | 1,463.69ms | 1,617.35ms |

기존 source bucket 2는 64MiB 예산에서 장면을 만들지 못해 직접 대응하는 완료 시간이 없다. 작은 표본에서 새 bucket 1 준비 중앙값은 약 6% 길었고, 한 표본은 2초에 가까웠다. 초기 준비가 항상 빨라진 변경으로 해석하지 않는다.

별도 탐색에서는 Qt/device를 먼저 만들고 추출→upload→그리기를 같은 프로세스에서 이어 실행했다. 추출 직후까지 peak RSS는 약 365→320MiB였지만 전체 실행의 peak RSS는 약 469→471MiB로 줄지 않았다. 이 탐색값과 위 작업 프로세스 값은 실행 환경·수명 범위가 다르다. 앱 전체의 상시 메모리나 VRAM이 45MiB 줄었다고 주장하지 않는다. 이 탐색은 매 범위마다 전체 항목을 재검색하던 초기 시제품이며, 최종 구현은 참조 인덱스를 갱신한다.

## 준비 후 그리기

1200×900, 96 DPI, 매번 새 retained scene, 결과 snapshot 재사용 없음. 3회 warm-up 뒤 15회씩 두 source bucket을 번갈아 측정했다. worker가 필요하면 완료를 기다리고, 단순 장면이면 직접 command list로 그리며 **동기 BGRA readback과 end_frame까지** 포함한다. 여기서는 두 장면 모두 직접 경로다. 추출·upload·장면 생성은 제외한다.

| ACB 2019 화면 배율 | bucket 1 중앙값 / P95 | bucket 2 중앙값 / P95 |
|---|---:|---:|
| 맞춤 | 24.39 / 29.98ms | 24.70 / 33.08ms |
| 100% | 18.58 / 20.68ms | 17.55 / 21.16ms |
| 200% | 17.14 / 23.07ms | 17.90 / 22.73ms |

이 표는 새/옛 알고리즘의 동일 해상도 속도 비교가 아니라, **새로 가능해진 더 높은 소스 해상도의 그리기 비용**을 보여준다. bucket 1의 native 입력·출력은 이전과 같고 그리기 알고리즘도 바뀌지 않았다. source bucket과 viewport 확대 배율은 서로 다른 값이다. 실제 CPU fallback 경로보다 몇 배 빨라졌다는 수치는 측정하지 않았다.

## 한계와 검증

최종 관련 회귀 검사 **176개 모두 통과**. GPU 알파·삽화·추출·색·실제 합성, 디스크/메모리 캐시, native backend, 작업 프로세스와 릴리스 패키징/노트 검사를 포함한다. Python 구문 검사와 `git diff --check`도 통과했다. 공개 도구의 `--raster-scale 2 --mode completed` 경로도 실제 ACB 2019로 실행 확인했다.

- ACB 2019 source bucket 4는 여전히 기존 64MiB 예산을 초과한다. 지원하지 못한 경우 CPU fallback을 유지한다. 전 페이지를 무제한 고해상도 이미지로 만드는 변경은 아니다.
- source bucket 1→2는 더 많은 원본 픽셀을 보존하므로 출력 자체는 달라질 수 있다. 동일 bucket 비교에서는 2015/2019의 1·2 모두 장면 항목과 이미지 bytes가 참조 결과에 일치했다. 2019 bucket 2의 비교 참조는 개인 실험에서만 원본 추출 한도를 늘린 뒤 기존 방식으로 결합해 만들었다. 제품의 한도는 올리지 않았다.
- 2019 bucket 1의 맞춤·100%·200% 실제 GPU readback은 이전 `09e46a3` 단계에서 저장한 결과와 byte 일치했다. bucket 2 맞춤 화면도 시각 검토했다.
- 합성 예제에서 기존에는 64bytes 한도로 실패하던 입력을 같은 한도로 성공시킨다. 공유 원본이 살아 있으면 보관·비용을 유지하는지, 보간 불일치·생성 예산·source index·두 원본 갱신 recipe를 검사한다. 이미지 전용 갱신이 한도에 걸린 뒤 worker 전체 추출로 복구하는 실제 파일 경로도 검사한다.

측정 원본과 결과는 소스에 포함하지 않는다. `tmp/gpu-alpha-stream/`의 `final-equivalence.json`, `quality.json`, `prepared/results.json`, `worker-memory/*.json`, `worker-memory-summary.json`, 탐색용 `memory/*.json`에 보관한다. 비교 기준은 `09e46a3`의 추출 후 알파 결합 경로다. 공개 측정 도구에는 `--no-alpha-stream`, `--raster-scale`을 추가했다.
