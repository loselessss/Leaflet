# 리더·편집기 프로세스 분리 — sPDF 1.20.0

구현일: 2026-08-31. 기준 저장소 `main` / `530e033`에서 시작했다.
동작 갱신: 2026-09-01, sPDF 1.22.0에서 같은 파일의 작업 모드 인계 후 원래 탭을 닫는다.
이 문서는 구현·검증 범위를 설명하며 배포 완료를 의미하지 않는다.
제품 이름은 sPDF다. 실제 GPU 벡터·글자 렌더러 교체와 조판 기능은 이번 범위 밖이다.

## 실행과 소유권

- `python run.py [문서]`는 `~/.spdf.json`의 `startup_workspace`를 사용한다.
  기본값은 `reader`. `--workspace reader` / `--workspace editor`로 이번 실행만 지정할 수 있다.
  UI는 **도움말 → 시작 모드**에 있다.
- 리더의 편집 모드와 편집기의 **파일 → 읽기 창 열기**는 `subprocess.Popen`으로
  동일 진입점을 다른 역할의 **별도 OS 프로세스**로 실행한다. 설치본은 같은 EXE를 역할 인자로 실행한다.
- 대상 프로세스가 문서를 정상적으로 열었다는 `opened` 응답을 보낸 뒤 원래 파일 탭을 닫는다.
  마지막 탭이면 원래 창과 프로세스도 종료한다. 실패·연결 끊김·15초 시간 초과에는 원래 탭을 유지한다.
- 실행 기록은 PID·역할·경로·요청 ID를 가진다. 같은 문서의 응답 가능한 프로세스는 재사용한다.
  종료된 프로세스는 재실행하며 15초 이상 응답이 없으면 새 프로세스를 열 수 있다.
  이전 프로세스를 자동 강제 종료하지 않는다. 새 편집기와의 저장 충돌은 파일 버전 검사로 막는다.
- `QProcess`의 부모 객체 파괴에 따른 종료나 `waitFor*` 호출을 사용하지 않는다.
  모드 인계로 원래 프로세스가 종료되어도 대상 프로세스의 이벤트 루프·문서·취소·OCR·복구 수명은 종료되지 않는다.
- 공통 코드는 재사용하지만 문서 객체, 파일 핸들, 화면·GPU 컨텍스트, 렌더 캐시, 타이머,
  실행 취소·다시 실행 상태는 공유하지 않는다. 편집기의 별도 페이지 구성 창과 상세 편집은
  해당 편집 프로세스 안에서 같은 문서·이력을 계속 사용한다.
- 페이지 구성 패널과 글자 편집 대화상자는 필요한 역할·명령에서만 불러온다.
  OCR 엔진을 리더에 미리 올리지 않는다. 기존 GPU 이미지 합성/CPU 대체 경로는 유지한다.

## 비동기 통신

`process_workspace.py`는 사용자 접근으로 제한한 `QLocalServer` / `QLocalSocket`을 사용한다.
무작위 엔드포인트와 세션 토큰으로 연결하며 비밀번호나 PDF 바이트는 보내지 않는다.

| 메시지 | 처리 |
| --- | --- |
| `hello` | 세션 토큰 확인 및 PID 연결 |
| `open` | 요청 ID·문서 경로·정제된 보기 상태로 Qt 이벤트 루프에서 열기 |
| `opened` | 실제 열기 성공/실패 완료 알림. 성공하면 원래 탭을 닫고, 실패·만료된 요청은 원래 탭 유지 |
| `heartbeat` | 1초 주기 생존 신호. 15초 무응답을 읽기 동작과 별도로 표시 |
| `saved` | 교체 완료 후 이벤트 ID·경로·파일 버전으로 리더 갱신 요청 |

프레임과 송수신 대기는 64 KiB로 제한하며 잘못된 인증·과대 메시지는 연결을 끊는다.
연결별 증가 번호로 오래된 메시지를 무시하고 이벤트 ID로 중복·전달 고리를 막는다.
연결 끊김과 시간 초과는 상태 표시줄로 안내하며 독서 기능을 막는 팝업을 띄우지 않는다.
저장 통지는 연결된 작업 창에만 전파한다. 다시 시작한 리더와 자동으로 재연결하는
전역 프로세스 관리자는 구현하지 않았다. 이 경우 문서를 다시 열어 디스크 저장본을 확인한다.

## 저장과 독립 창 갱신

일반적인 모드 전환에서는 같은 파일의 원래 탭을 닫으므로 저장 시 갱신할 리더가 남지 않는다.
사용자가 별도로 연 독립 리더나 이전 연결 창이 존재하는 경우에만 아래 안전한 갱신 절차를 적용한다.

1. 각 독립 작업 창은 입력 파일을 전용 임시 폴더로 복사한 뒤 그 사본을 연다.
   복사 전후 파일 버전이 다르면 재시도하도록 실패 처리한다. 암호화된 입력은 암호화 그대로 복사한다.
   전체 PDF를 RAM으로 읽어 두는 방식이 아니며 기존 렌더 캐시 상한을 유지한다.
2. 저장은 목적지와 같은 폴더의 임시 PDF를 완성하고 재개방·페이지 수 확인·flush 후 진행한다.
3. 목적지별 OS 잠금을 **기다리지 않고** 얻는다. 잠금 중단·프로세스 충돌 시 OS가 잠금을 해제한다.
   Windows에서는 `.spdf-save.lock`을 공유 불가·닫을 때 삭제되는 핸들로 열어 이중 소유를 막고,
   저장 종료나 프로세스 충돌 시 자동 삭제한다. 다른 OS에서는 잠금 파일을 유지한다.
4. 열린 시점/직전 저장의 파일 버전과 현재 목적지가 일치하는지 검사한다.
   다른 편집기가 저장했으면 현재 편집 상태를 유지하고 다른 이름으로 저장하도록 안내한다.
5. 기존 파일을 별도 임시 백업으로 완성한 뒤 `.bak`을 교체한다. 원본 버전을 다시 확인하고
   `os.replace`로 PDF를 교체한다. 성공하면 이번 저장의 `.bak`을 삭제하고, 실패하면
   원본·편집 상태와 복구용 백업을 유지한다. 다른 프로그램이 백업을 열고 있으면 삭제하지 못할 수 있다.
6. 교체 완료만 통지한다. 리더는 사본 복사를 백그라운드에서 수행하고, 파일 버전과 문서 유효성을
   확인한 뒤 GUI 스레드에서 문서를 바꾼다. 기존 문서는 새 문서 준비까지 계속 살아 있다.
   교체 직전의 읽던 쪽·배율·스크롤 위치를 적용한다.
7. 탭당 복사 작업은 하나이며 추가 통지는 최신 요청으로 합친다. 15초 갱신 시간 초과,
   오래된 통지·늦은 복사 완료·닫힌 탭·손상된 PDF는 마지막 정상 문서를 교체하지 않는다.
   Windows가 실패한 파서의 임시 파일 핸들을 잠시 유지하면 정리는 다음 이벤트에서 재시도한다.

별도로 연결된 리더가 있을 때 그 핸들을 닫고 편집기 응답을 기다리는 저장 단계가 **없다**.
따라서 저장 시작 전, 잠금 확보 중, 파일 교체 직전, 교체 직후에 편집기가 중단되어도
해당 리더가 빈 문서로 남지 않는다. 교체 후 통지 전에 중단되면 디스크에는 새 완성본이
있어도 별도 리더는 기존 정상 사본을 유지한다. 일반 모드 인계로 닫힌 리더에는 적용되지 않는다.
다른 프로그램이 원본을 잠그면 저장이 실패할 수 있다. 원본 잠금을 강제로 해제하지 않는다.
비협조적 외부 작성자의 동시 쓰기나 시스템 전원 상실·저장 장치 장애까지 완전한 트랜잭션을 보장하지 않는다.

## 미저장 복구와 외부 API

기존 복구 저장소는 편집 프로세스마다 고유 세션과 생존 잠금을 소유한다. 리더 종료는
편집기의 체크포인트를 삭제하지 않는다. 리더에서 복구 목록을 확인할 때 잠시 얻은 세션
잠금은 편집기를 실행하기 전에 풀어, 살아 있는 리더가 복구 사본을 점유하지 않게 했다.

기존 30초 주기, 보호 PDF·512 MB 초과 사본 제외, 원본을 덮어쓰지 않는 복구 후 Save As
정책을 유지한다. 체크포인트 이후의 마지막 변경까지 복구된다는 의미는 아니다.
정상 종료 시 전용 사본을 정리하지만 강제 종료 후 남은 사본은 OS 임시 파일 정리가 필요할 수 있다.

외부 `new_window` / `AppWindow`의 `read_only`, `annotations_enabled`,
`autosave_annotations` 및 기본 자체 업데이트 OFF는 바꾸지 않았다.
`workspace_mode`를 생략하는 내장 리더는 호스트 프로세스에 그대로 속하며, 편집 프로세스 실행 버튼을
노출하지 않는다. 별도 실행 작업 창에서 시작한 자식은 부모의 업데이트 허용 여부를 인자로 이어받는다.

## 검증 범위

Windows, Python 3.12.13, PyQt5 5.15.11 / Qt 5.15.2, PyMuPDF 1.28.2에서 확인했다.
자동 GUI 검증은 offscreen / CPU 표시 환경이며 인쇄는 QPrinter PDF 출력이다.

최종 `ci_test_runner.py` 전체 **261개 통과, 실패·건너뜀 0개**, 실행기 종료 코드 0을 확인했다.
실제 PID 기록 예시는 리더 `22048` / 편집기 `23132`다. 실행마다 PID는 달라진다.
QtNetwork 타입을 창 생성 전에 초기화하도록 보완한 뒤 외부 모드 테스트 묶음을
8회 연속 통과했고, 창 닫기·명시적 메모리 회수·다시 열기·저장 반복 검사도 통과했다.
기존 번역 지연 처리를 제거하거나 오류를 무시해서 통과시킨 것은 아니다.

| 확인 사항 | 검증 |
| --- | --- |
| 실제 다른 PID·열기 완료·재사용·재실행 | 실제 sPDF 진입점을 실행하는 테스트 프로세스 |
| 같은 파일의 모드 인계 | 대상 열기 성공 뒤 원래 탭·마지막 창 종료, 실패·시간 초과에는 원래 리더 유지 |
| 편집 우선 설정·별도 리더·편집 전용 패널 지연 로드 | 실제 프로세스와 로드 모듈 검사 |
| 정상 종료·강제 종료·네이티브 충돌·무응답 | 테스트 소유 프로세스에만 주입 후 리더 탐색·확대·검색·PDF 인쇄 출력 |
| 저장 시작 전·OS 작성 잠금 중·교체 전후 중단 | 각 단계에서 테스트 편집기 중단, 원본 또는 새 완성본·백업·리더 사본 확인 |
| 정상 저장·Save As | 별도로 연결된 리더가 있으면 내용 갱신과 쪽·배율·스크롤·원본 경로 유지 |
| 연결 끊김·잘못된 인증·과대 메시지·오래된 알림 | IPC 테스트, 문서 보존 확인 |
| 복사 시간 초과·늦은 완료·손상 파일 | 마지막 정상 문서 보존 및 읽기 기능 확인 |
| 다른 편집기 충돌·실제 Windows 파일 핸들·백업 실패 | 저장 거부, 원본·이전 백업·미저장 상태 유지 |
| 리더 프로세스 강제 종료 뒤 편집·복구 | 살아 있는 편집기 체크포인트와 이후 복구 PDF 확인 |
| 기존 기능 | 전체 `ci_test_runner.py`, 외부 API·주석·페이지 구성·undo/redo·OCR 좌표·번역 수명 포함 |

`tests/workspace_process_fixture.py`만 장애 주입과 테스트 제어 파일을 읽는다.
제품 코드에는 테스트용 강제 종료·무응답 명령이 없다. 기존 테스트 실행기의 Windows 오류창 억제와
위젯 번역 지연 처리를 유지했다. Qt DLL 종료 문제를 피하는 기존 테스트 정책에 따라 정상 종료
테스트도 창의 closeEvent 정리 이후 테스트 진입점에서 종료한다.

미검증: 실제 GPU 장치/드라이버에서의 화면 품질·GPU 장애, 물리 프린터 출력, OCR 모델을 사용한
실제 인식 전체 흐름, PyInstaller 설치 EXE 및 설치 프로그램 재빌드, 네트워크 드라이브·전원 상실.
별도 프로세스 주소 공간은 검증했지만 시스템 전체 자원 고갈이나 GPU 드라이버 장애의 완전한 격리는 보장하지 않는다.
