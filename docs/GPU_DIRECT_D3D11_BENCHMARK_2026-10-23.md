# D3D11 직접 마스크 합성 비교

측정일: 2026-10-23 · Leaflet 1.37.1 개발 중 · Intel Iris Xe · ABI 24

## 판단

**이번 직접 D3D11 합성 후보는 기본 경로에 채택하지 않는다.** 기존 클립·마스크의 마지막 합성을 D3D11 fullscreen-triangle shader로 바꾸는 두 방식을 구현했다. 실제 D3D11 실행과 정확도는 검증했지만 완료 시간의 이득이 조건별·실행별로 달랐다. 결과 복사 후보의 최종 15회 재측정에서 ACB 2015 맞춤은 약 22%, 200%는 약 38% 느려졌고, 100%는 약 11% 빨라졌다. 앞선 비교에서는 100%도 느렸다.

메모리 감소 관측은 있었다. 계측을 제거한 별도 프로세스 비교에서 ACB 2015 peak RSS가 기준 약 655MiB, 결과 복사 후보 약 617MiB였다. 다만 속도 악화가 큰 조건이 있어 기본 동작을 바꾸지 않았다. 앞서 채택한 최대 256슬롯 수명 계획·묶음 할당은 그대로 유지한다. 실험 C++·shader·빌드·측정 자료는 개인 폴더에 보관했다.

## 후보의 범위

- 일반 clip과 적용 완료된 soft mask를 닫을 때 쓰는 마지막 3입력 합성만 직접 처리했다. D2D 도형·글자·bitmap·gradient·coverage 생성, 복잡한 blend mode 1~15, 비격리 그룹 보간 등은 기존 경로다. 모든 합성을 새 실행기로 옮긴 비교는 아니다.
- 기존 strict float shader와 같은 식 `Q8(B*(1-M)) + Q8(S*M)`을 사용한다. 각 항을 UNORM8로 반올림하고 최종 BGRA8 출력에서 clamp한다. 근사·해상도 축소·새 이미지 결과 캐시는 없다.
- VS/PS는 vs_4_0·ps_4_0, /Gis /O3로 빌드했다. input은 Texture2DArray view로 통일하고 Load로 정수 texel을 읽는다. DXGI surface의 실제 subresource를 확인해 array slice를 지정한다. BGRA8·single sample·한 mip·bitmap과 같은 texture 크기만 지원하며 그 외에는 D2D로 돌아간다.
- **배경 복사 유지(inline)**: 기존 CopyFromBitmap/Flush로 backdrop을 확보한 뒤, D3D11이 원래 target에 바로 쓴다. 기존 복사 뒤 추가 D2D Flush는 넣지 않는다.
- **결과 복사(copyback)**: D2D Flush 뒤 기존 target의 배경과 content/mask를 읽어 임시 표면에 합성하고, CopySubresourceRegion으로 해당 영역만 원래 target에 복사한다. 배경 복사 대신 결과 복사를 한다. 임시 표면에 render-target bind flag가 없으면 기존 경로로 처리한다. 복사 1회 자체를 없앤 방식이 아니다.
- geometry의 순서·mask 생성/적용·COPY/knockout 규칙은 유지한다. 별도 depth/blend/raster 상태와 viewport를 설정하고, 입력·출력을 해제한 다음 원래 D3D 상태와 D2D target을 복원한다.
- shader·고정 상태·buffer·context-state 객체를 parent와 worker가 공유하는 후보까지 비교했다. constant buffer와 context-state의 변경은 공유 장치 잠금 안에서 직렬화한다. 최종 속도 표는 이 공유 버전이다. 작업별 bitmap view는 해당 타일의 arena/target 수명 안에서만 최대 257개까지 보관하고, 저장소 포기·다음 타일 때 해제한다.

초기 프로토타입에서는 worker에 ID2D1Multithread 참조를 전달하지 않아 직접 D3D 구간의 잠금이 빠졌다. 동시 UI/worker 그리기 검사에서 출력 오류가 나서 수정했다. 기본 D2D 렌더러의 문제를 고친 것으로 해석하지 않는다. 수정한 두 후보는 기존 허용치를 바꾸지 않고 모두 통과했다.

상태 공유·복원 및 잠금의 근거: [SwapDeviceContextState](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_1/nf-d3d11_1-id3d11devicecontext1-swapdevicecontextstate), [D2D/D3D 다중 스레드 보호](https://learn.microsoft.com/en-us/windows/win32/direct2d/multi-threaded-direct2d-apps). D3D device context를 직접 조작하는 구간에는 D2D API 내부 잠금만으로 충분하다고 가정하지 않았다.

## 비교 조건

기준은 직전 작업에서 채택한 256슬롯 수명 계획을 포함한 로컬 개발 DLL이다. 출시 v1.37.0과의 비교가 아니다. ACB 2019·2015 첫 페이지, 1200×900 viewport, 96 DPI, 맞춤·100%·200%, raster scale 1이다. 매 표본 새 scene identity를 사용한다.

요청부터 전체 정밀 atlas 완료·UI import까지 측정한다. Python PDF 해석·불변 geometry upload·retained scene 생성은 타이머 밖이고 worker 준비·타일 계획·합성은 안이다. GPU timestamp만의 측정이 아니다. 각 조건 3회 예열 후 15회 측정하고 같은 프로세스에서 library 순서를 교차·회전했다. UI polling은 1ms이며 다른 GPU 테스트·빌드·계측은 동시에 실행하지 않았다. 표의 양의 %는 단축, 음의 %는 악화다. 단위 ms.

## 메모리

계측 코드를 제거한 DLL을 문서·library당 각각 별도 프로세스로 실행한 peak 값(MiB)이다. 각 보기 3회 예열+2회 표본, 총 15개 프레임을 실행한다. 추출·업로드·readback·Qt·드라이버 사용자 영역 메모리를 포함한 프로세스 값이며 GPU VRAM이나 마지막 합성 표면만의 크기가 아니다.

| 문서 | 지표 | 기준 | 배경 복사 유지 | 결과 복사 |
|---|---|---:|---:|---:|
| ACB 2019 | Peak RSS | 575.68 | 571.20 | 568.12 |
| ACB 2019 | Peak commit | 643.73 | 616.52 | 612.02 |
| ACB 2015 | Peak RSS | 655.13 | 606.91 | 617.31 |
| ACB 2015 | Peak commit | 690.58 | 635.97 | 650.95 |

ACB 2015 결과 복사 후보의 peak RSS는 이 관찰에서 약 37.82MiB, peak commit은 약 39.63MiB 낮았다. 별도 QPC/호출 수 진단 프로세스에서도 RSS는 기준 654.30→610.91MiB로 낮게 관찰됐다. 각 비교는 library당 한 프로세스 실행이며 통계적 메모리 절감 보장은 아니다. 다른 실행의 메모리·속도 표본을 합쳐서 한 프레임의 효과로 발표하지 않는다.

## 초기 객체 수명 후보와 CPU 진단의 한계

정적 D3D 자원을 작업마다 생성·해제하는 초기 후보도 15회씩 비교했다. 예를 들어 ACB 2019 맞춤은 기준 33.96ms에 배경 복사 유지 62.58ms·결과 복사 63.47ms였고, ACB 2015 맞춤은 기준 218.87ms에 234.05ms·237.80ms였다. 최종 후보는 장치에 속한 객체의 공유를 포함한다. 렌더 결과 이미지를 재사용한 것은 아니다.

두 실행의 절대 시간 차이를 객체 공유만의 효과라고 단정하지 않는다. 별도 QPC 진단은 초기화·view 준비·CPU 명령 발행·상태 복원·명시적 Flush·잠금 대기 및 작업 정리를 나눴다. 초기화·renderer 해제만으로 초기 실행의 큰 완료 시간 차이를 전부 설명할 근거는 없었다. 해당 타이머는 CPU 경과 시간이고 GPU 실행·드라이버 내부 동작을 분리한 값이 아니다.

배경 복사 유지의 direct 함수 타이머에는 호출 전 copy helper의 Flush가 빠지고, 결과 복사의 direct 함수에는 Flush가 들어간다. 두 함수의 포괄 시간을 곧바로 서로 비교하면 안 된다. 상태 swap은 CPU 명령 발행 구간의 부분집합이므로 그 구간에 다시 더하지 않는다. 계측 로그의 시간은 위의 비계측 성능 표와 분리했다.

## 검증과 판단의 범위

- 수정한 두 기본 후보 및 정적 자원 공유 후보는 각각 기존 합성 검사 17개를 통과했다. COPY·비격리 그룹·중첩 mask·DPI·기울어진 경계·작업 교체·동시 UI/worker 그리기 검사를 포함한다.
- 별도 WARP 결과 복사 후보 17개와 강제 초기화 불가 fallback 후보 17개도 통과했다. 기존 허용 오차는 바꾸지 않았다.
- 256×256개의 모든 source alpha·mask coverage 조합을 독립 CPU 식과 비교해 byte 단위로 일치했다. 기준·두 공유 후보·WARP·fallback에서 통과했다. 계측 후보에서도 해당 장면의 D3D Draw 1회·fallback 0회를 확인했다. 한 색상 계열과 흰 배경을 사용하는 조합 검사이며 모든 가능한 RGBA 조합의 증명은 아니다. 투명 배경·색상·중첩 상태는 별도 기존 검사에 포함된다.
- 초기 두 후보 12개, 공유 후보 12개, 결과 복사 재측정 6개 등 저장한 포스터 후보 화면 30개를 각각 기준과 비교해 모두 픽셀 차이 0이다. 모든 성능 case는 오류 없이 예정된 표본 수를 완료했다.
- C++17 /W4 /WX /O2와 strict HLSL 빌드가 통과했다. 공개 ABI는 24다. 원본 C++·수명 계획 header·기본 DLL의 byte 동일성을 확인했다.

현재 마지막 마스크 경로는 이미 하나의 custom D2D effect로 단순화되어 있다. 이번 후보는 같은 수의 합성 단위를 D3D11 Draw로 옮기며, D2D↔D3D 상태 복원·view 준비·자원 binding과 복사 의존성도 필요하다. API를 직접 부르는 변경만으로 합성 단위 수가 줄지는 않는다. 이런 추가 비용이 이득을 상쇄할 수 있다는 구조적 해석은 가능하지만, 이번 계측만으로 GPU 활성 시간이나 특정 드라이버 동작을 주원인으로 확정하지 않는다.

후속 전용 합성기는 독립적인 패스를 더 큰 단위로 묶어 전환·제출 자체를 줄이는 구조가 필요하다. 겹치는 backdrop·COPY·mask 의존성 때문에 임의로 표시 순서를 재배열해서는 안 된다. 이 실험의 미채택을 D3D11 전용 합성기 전체의 가능성이 없다는 결론으로 일반화하지 않는다.
