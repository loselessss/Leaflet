# 첫 정밀 타일 지연 분석과 사각형 클립 비교 (2026-10-19)

화면 밖 명령 묶음 제외까지 적용한 직전 1.37.0 개발 DLL을 기준으로, 첫 정밀 타일의 지연을 분리 측정하고 후보를 비교했다. 4901da6이나 과거의 440.8ms 측정과 절대시간을 직접 비교하지 않는다. 최종 구현은 target 전체를 덮는 정확한 사각형 클립의 불필요한 합성만 생략한다. 작은 첫 타일 추가와 배경 복사 순서 변경은 제외했다.

ACB 2019 화면 맞춤과 200%는 두 회차에서 모두 완료시간이 줄어 사각형 생략을 유지한다. 100%의 개선은 반복되지 않았다. ACB 2015는 전체 완료시간의 일관된 단축을 확인하지 못했고 일부 조건은 더 느렸다. 이 변경으로 ACB 2015의 큰 지연을 해결했다고 해석하지 않는다. 30ms 확인 간격으로 인해 ACB 2019의 완료시간 차이에는 확인 주기를 한 번 덜 기다리는 효과도 포함된다.

## 지연이 발생한 구간

ACB 2015는 네이티브 명령 33,270개, scope 10,864개 중 simple scope 5,592개다. 진단용 별도 DLL에 QueryPerformanceCounter 타이머를 삽입했다. 조건별 준비 3회 뒤 2회 측정의 중앙값이며, 정식 성능 비교는 아래의 계측 없는 DLL로 수행했다.

단위 ms. 공개·첫 가져오기 완료는 요청 시점부터의 누적 시간이고, 나머지는 해당 구간의 경과 시간이다. 타이머는 CPU가 관측한 API 호출·driver 대기 시간이며 GPU timestamp가 아니다. 중첩 구간은 겹치므로 열을 모두 더하면 안 된다. 계측 자체의 오버헤드와 시스템 상태 차이가 있어 아래 비계측 완료시간과 섞어 계산하지 않는다.

- 화면 맞춤의 원래 첫 타일은 512×512px다. draw 17,176회, capture 진입 4,340회, 종료 4,523회, mask 생성/전환 각 183회, scratch 요청 4,008회, Flush·CopyFromBitmap 각 2,549회가 기록됐다. 클립 종료 합성은 1,090회다.
- 요청 준비와 가져오기보다 중첩 합성의 replay가 지배적이다. 특히 copy 전 Flush에 관측 시간이 많이 모였다. 이 수치만으로 GPU 연산만의 비용과 CPU/driver 대기를 분리할 수는 없다.
- 사각형 생략의 별도 계측에서는 화면 맞춤 첫 타일의 클립 10개가 빠져 복사 경계가 2,549→2,529회로 줄었다. ACB 2015 전체 병목을 없애는 규모는 아니다.

## 최종 구현

- MOVE + 세 LINE + CLOSE, 또는 시작점으로 돌아오는 LINE이 하나 더 있는 정확한 사각형만 인식한다. 네 모서리는 축 정렬되고 면적이 있어야 한다. 경로와 장면/worker 복제에 내부 bool 하나를 보존하며 공개 ABI 24는 유지한다.
- 변환 후에도 축 정렬이며 현재 target 전체에 추가 2물리px 여유까지 덮을 때만 클립 capture를 생략한다. source·mask·backdrop 예약, 시작/종료 복사와 최종 합성을 건너뛰되 scope는 남겨 이전 transform과 primitive blend를 복원한다.
- 일반 경로, 구멍, 추가 꼭짓점, 부분 coverage와 shear는 기존 경로를 유지한다. 중첩 knockout 내부의 클립 내용은 기존과 같은 SOURCE_OVER로 그리고 닫을 때 부모 상태를 복원한다. 타일 격자·해상도·결과 캐시·메모리 예산을 늘리지 않는다.

## 비계측 ACB 비교 조건

- Windows / Intel Iris Xe hardware / PyMuPDF 1.28.2 / viewport 1200×900 물리px / 96 DPI. 두 PDF의 첫 페이지를 화면 중앙에 두고 화면 맞춤·100%·200%를 비교한다. 이미지 준비 배율은 1로 고정한다.
- 각 표본마다 새 네이티브 장면 identity를 만들어 페이지·그룹·정밀 타일 결과 재사용을 막는다. 공통으로 준비한 geometry·이미지 업로드 자원은 유지한다. 최초 파일 열기·추출·업로드 및 확대 이미지 재추출 시간은 포함하지 않는다.
- 조건당 준비 3회 + 측정 15회, 두 DLL을 번갈아 실행하고 순서를 교대한다. 회차를 다시 실행할 때 DLL 준비 순서도 반대로 한다. 다른 GPU 테스트·빌드는 함께 실행하지 않았다.
- 실제 리더의 30ms 완료 확인 간격을 사용한다. 요청부터 전체 정밀 viewport atlas의 준비·가져오기 완료까지 측정하며 최초 PDF 열기·90ms 입력 안정화·화면 Present/vsync를 제외한다. 첫 타일도 확인 간격의 영향을 받는다.
- 아래 두 최종 DLL은 동일한 원래 타일 격자이므로 첫 타일 면적도 같다. 시스템 상태에 따라 절대시간이 크게 변할 수 있어 같은 회차 안에서 비교한다. P95는 15개 표본의 nearest-rank 상위값이다.

## 제외한 후보

- 배경을 scope 시작 시점에 확보해 재사용하는 두 변형은 중첩 클립에서 출력이 달라졌다. 추가 진단 Flush를 넣으면 증상이 사라져, 현재 의존성/제출 보장을 확인하지 못한 상태로는 유지하지 않았다. 최종 소스에는 포함하지 않는다.
- 중앙 512px 타일을 작은 타일과 나머지 조각으로 분할한 후보는 일부 최종 픽셀이 달라지고 ACB 2015 100% 완료시간도 늘었다. 제외했다.
- 사각형 생략과 함께 원래 격자 앞에 128×128px 중앙 타일 하나를 추가한 조합 후보는 두 문서 여섯 조건의 최종 BGRA가 일치했다. 하지만 ACB 2015 화면 맞춤에서 첫 표시 408.6→134.6ms와 함께 전체 완료가 464.7→564.0ms(+21.4%)로 늘었다. 100%에서는 첫 표시 404.2→43.2ms, 전체 1048.9→898.3ms였지만, 화면 맞춤의 전체 지연 악화를 수용하지 않아 제외했다. 작은 첫 영역은 원래 첫 타일 면적의 1/16이므로 동등 면적 가속으로 해석하지 않는다.
